# PATCH-039 KURE-v1 시작 준비 평가

## 목적

Streamlit 첫 화면을 KURE-v1 초기화가 막지 않게 하고, 이미 받은 모델이 있는 환경에서는
불필요한 Hugging Face 네트워크 확인을 피한다. 검색 정확도와 모델 자체는 변경하지 않는다.

## 채택 구조

1. 채팅 이력과 입력창을 먼저 렌더링한다.
2. `st.cache_resource`에 저장한 단일 `BackgroundServiceLoader`가 KURE-v1을 준비한다.
3. 별도 Streamlit fragment가 1초마다 `준비 중/완료/실패` 상태만 갱신한다.
4. 준비 전에 일반 질문이 제출되면 사용자 질문을 먼저 표시하고 동일한 Future를 기다린다.
   첨부 파일 OCR보다 질문 표시가 늦는 기존 문제는 별도 PATCH-040 범위다.
5. 실패한 Future만 재시도할 수 있어 rerun이나 복수 질문으로 모델이 중복 적재되지 않는다.
6. SentenceTransformer는 `local_files_only=True`로 캐시를 먼저 열고, 캐시 부재를 뜻하는
   `OSError`일 때만 온라인 다운로드 경로로 전환한다.

## 2026-09-02 로컬 측정

- 환경: macOS, Python 3.13 가상환경, KURE-v1 로컬 캐시 존재, 외부 네트워크 차단
- 측정 단위: 새 Python 프로세스에서 `get_default_service()` 최초 생성
- 첫 화면 표시 시간은 브라우저 렌더링이 아니라 백그라운드 제출 함수의 반환 시간을
  대리 지표로 사용했다. 실제 브라우저 First Contentful Paint는 별도 측정이 필요하다.

| 조건 | UI 스레드를 막는 시간 | 검색 서비스 준비 시간 | 결과 |
| --- | ---: | ---: | --- |
| 기존 온라인 확인 경로 | 60초 이상 | 측정 중단 | 캐시가 있어도 Hugging Face 설정 파일별 HEAD 재시도가 반복됨 |
| 로컬 캐시 우선 + 백그라운드 | 0.0001초 | 4.6238초 | 네트워크 재시도 없이 캐시에서 준비 완료 |

프로세스 전체 wall time은 5.70초였다. 샌드박스에서 `/usr/bin/time -l`의 메모리 통계
수집이 허용되지 않아 최대 RSS는 기록하지 못했다. 기존 경로는 60초가 지난 뒤에도
네트워크 재시도가 계속되어 중단했으므로 정확한 완료 시간이 아니라 하한값이다.

## 대안과 운영 판단

| 대안 | 장점 | 제약 | 판단 |
| --- | --- | --- | --- |
| 동기 사전 로딩 | 첫 질문 시 모델 준비 완료 | 첫 화면과 입력창을 수 초~수십 초 차단 | 미채택 |
| 지연 로딩만 적용 | 첫 화면이 빠름 | 첫 질문에서 전체 모델 준비를 시작 | 단독 사용 안 함 |
| 백그라운드 단일 준비 | 화면을 먼저 표시하고 중복 적재 방지 | 매우 빠른 첫 질문은 남은 준비 시간을 기다림 | 채택 |
| 배포 이미지에 모델 캐시 포함 | RunPod 시작 시 다운로드 제거 | 이미지 크기와 빌드 시간이 증가 | 최종 이미지에서 권장 |
| RunPod 시작 후 워밍업 | 시연 전 준비 완료 가능 | Pod 재시작마다 워밍업 확인 필요 | 데모 운영 절차로 권장 |

## 남은 실기기 측정

- Windows에서 첫 화면 표시, 모델 준비 시간과 최대 메모리
- 최종 RunPod 이미지에서 캐시 포함 전후의 cold start와 첫 질문 전체 응답 시간
- 브라우저 Performance 도구를 사용한 실제 First Contentful Paint

위 항목은 해당 실행 환경이 준비된 뒤 같은 명령과 질문으로 기록한다. 로컬 측정값을
Windows나 RunPod 성능으로 일반화하지 않는다.
