# MySQL 기반 지식 데이터·리트리버·LLM 연결 실행 계획

작성일: 2026-09-18

상태: 공용 `Lens_knowledge` DB의 원문·청크·이력 이전, MySQL 단독 내보내기, 원문 추가·교체·삭제·재청킹, 검색 배포본 생성·활성화·되돌리기를 검증했다. 실제 LLM 서버와 다른 팀원 PC의 실행 검증은 미완료다. 사용자는 실제 LLM 서버 준비 전까지 검색 연결을 우선 진행하도록 지정했다.

2026-09-18 구현 결과: [MySQL 실행 안내](../mysql-data.md), [이전 검증 기록](mysql-transfer-validation.json), [원문·검색 갱신 검증 기록](mysql-update-validation.json). 공용 MySQL 8.4.11의 데이터·메타데이터를 원본과 비교했고 공용/로컬 내보내기 파일이 일치했다. 관련 테스트 109개와 하위 테스트 86개가 통과했다. 아래 초기 현황은 작업 시작 당시의 기록이며, 전체 검색 품질 기준선이나 실제 LLM 완료를 의미하지 않는다.


사용자 요청으로 2026-09-18 작업을 일시 중단했다. 새 Python 3.12 가상환경에서 패키지 설치·의존성 검사·shared-v3 배포본 검증은 통과했다. 모델 다운로드는 중단했으며 새 가상환경의 실제 검색은 미검증이다. [설치 검증 및 중단 기록](mysql-clean-install-validation.json)을 참고한다. 기존 배포본과 공용 DB는 보존했고, 후속 작업은 재개 요청 이후 진행한다.

## 1. 목표와 완료 범위

2026-09-18 검색 연결 검증: `mysql_search`의 생성·검증·활성화·질의 명령과 기존 앱 검색 진입점 연결을 구현했다. 실제 배포본으로 89개 질문에서 이전 전후 결과가 일치했다. 같은 PC의 원본 DB 없는 별도 설치 폴더에서도 앱 검색 진입점·모의 LLM 입력 전달을 확인했고, 네 채널의 실제 근거를 공용 MySQL 원문·출처까지 추적했다. [검색 검증 기록](mysql-search-validation.json)과 [팀 실행 안내](../mysql-search.md)를 참고한다. 다른 PC와 실제 LLM 검증은 아직 완료하지 않았다. 기존 판례 평가 정답 ID 중 8개가 현재 코퍼스에 없어 검색 품질 완료 판정과 이전 결과 일치 판정을 구분한다.

법령·판례·기관 안내 원문과 청크를 공용 MySQL에서 관리하고, 동일한 검색 데이터를 팀원에게 제공해 기존 리트리버와 LLM을 쉽게 연결·실행하게 한다.

1. 현재 데이터·청크·검색 기준 확정
2. MySQL 스키마·연결·원문 및 메타데이터 이전
3. 청킹 → MySQL 저장 → 검색용 청크 내보내기
4. BM25·Chroma 리트리버 연결 및 갱신
5. 기존 LLM 연결·출처 추적·검색 회귀 검증

리트리버는 실행 코드다. MySQL에는 원문·청크·출처·버전·검색 메타데이터를 저장한다. BM25는 배포된 청크로 구성하고, 벡터 검색은 기존 Chroma를 유지한다. 공용 MySQL에 연결하는 것만으로 팀원의 검색 데이터가 갱신되지는 않는다.

회원·로그인·대화 DB, UI 재설계, OCR, LLM 교체·파인튜닝은 이 계획의 구현 범위에 포함하지 않는다. 기존 생성 담당자와 검색 결과 계약 및 실제 앱 통합을 함께 검증한다.

### 코드 및 실행 준비 상태

- `src/database/config.py`, `relational.py`는 SQLite 파일 경로·연결 중심이다.
- 실제 배포 DB에는 기본 `schema.sql` 외에 판례 버전·관찰·별칭 테이블과 추가 컬럼이 있다. 기본 스키마만 변환하면 이전 대상이 누락된다.
- `knowledge_release.reexport_case_chunks()`는 DB 본문을 확인한 후 기존 JSONL을 복사한다. MySQL만으로 내보내는 구현으로 교체·확장해야 한다.
- 판례 JSONL 중 11건에 `source_page_sha256`, `indexed_official_section`, `summary_type`이 있다. `observed_at`, `corpus_active`는 8,366건에만 있다. 필드 없음과 빈 값·NULL·false를 임의로 같은 값으로 바꾸지 않는다.
- 안내 JSONL의 `published_at_source`, 법령 JSONL의 `version` 등도 DB와의 필드별 대응을 조사해야 한다.
- `data/database/knowledge.sqlite3`, `data/database/civil.sqlite3`, 기본 `data/chunks/*.jsonl`, `data/case_corpus/runtime-profile.json`은 점검 시 존재하지 않는다. 현재 앱 전체 검색이 준비됐다고 볼 수 없다.
- `server_build.py`에는 기본 법령 청크 178·민법 26·판례 시드 26·안내 6을 검증하는 코드가 있다. 이는 이번에 실측한 건수가 아니며, 판례 배포의 법령 133청크와도 다르다. 실제 활성 채널별 데이터 선정이 필요하다.
- 기존 `Evidence`, `RetrievalResult`, `answer_question()` 및 판례 LLM 연결 검사 스크립트를 재사용할 수 있다.
- 과거 문서에는 Ollama 메모리 부족 실패가 기록돼 있다. 현재 실제 LLM 가용 여부는 재확인하지 않았으므로 현재 장애 또는 성공으로 단정하지 않는다.

## 3. 목표 데이터 흐름과 책임

```text
수집·정제된 법령 / 판례 / 기관 안내
                 ↓
MySQL: 원문·버전·출처 → 청킹 → 청크·검색 메타데이터
                 ↓ 같은 스냅샷에서 내보내기
검색 배포본: manifest + 유형별 JSONL + Chroma + 검색 설정
                 ↓ 팀원 설치·검증·활성화
질문 → 기존 BM25·dense·RRF → Evidence / RetrievalResult
                 ↓ 기존 생성 체인
LLM 답변 + 출처 → chunk_id → MySQL 문서·원문 버전
```

- 데이터 관리 담당: MySQL 적재·갱신, 배포본 생성·검증·게시를 수행한다.
- 팀원: 동일한 배포 버전과 임베딩 모델을 설치하고 기존 검색·LLM 연결 함수를 사용한다. 개인별 재수집이나 임의 청킹이 필요 없어야 한다.
- MySQL 읽기 계정과 적재·스키마 변경 계정을 분리한다. 검색 실행은 검증된 배포본을 사용하므로 요청마다 MySQL에 의존할 필요가 없다.
- 공용 MySQL을 기준 저장소로 하고 JSONL·Chroma를 재생성 가능한 산출물로 관리한다. 최초 이전 입력으로 SQLite와 JSONL을 함께 사용할 수 있으나 이후 내보내기는 기존 JSONL 없이 가능해야 한다.
- 데이터 갱신에서 사용자 검색 반영까지는 `적재 → 배포본 생성 → 검증 → 활성화` 단계가 필요하다. 이 지연을 운영 문서에 설명한다.

## 4. 단계별 실행 계획

### 1단계 — 데이터와 검색 기준 확정

작업:

- 기본 법령·민법·안내의 원천 레코드와 판례 배포본을 각각 조사한다. 현재 앱의 판례 채널 교체 동작을 기준으로 활성 코퍼스 목록을 확정한다.
- 기본 레시피를 별도 출력 경로에서 준비하고 실제 테이블·청크 건수를 기록한다. 판례 배포본 안의 법령·안내를 기본 채널에 무조건 합치지 않는다.
- DB별 실제 DDL, 테이블 수, PK·FK, 내용 해시, JSONL 필드, 원문 위치·보존 상태를 기록한다. 수집 원문 전문이 없는 자료는 누락 사실을 표시하고 확보 작업을 분리한다.
- 코퍼스별 ID 충돌을 검사한다. 서로 다른 코퍼스의 같은 ID·다른 본문은 자동 병합하지 않는다.
- 임베딩 모델 revision·차원, 법령·민법·판례·안내별 필터·후보 수·RRF·반환 수, 앱 라우팅 설정을 기록한다.
- 평가셋별 정답 ID가 활성 코퍼스에 존재하는지 확인한다. 시드 26건의 성능을 판례 8,377건의 기준으로 사용하지 않는다.
- 현재 데이터로 유형별 검색 결과·지표·지연시간을 저장한다. 미준비 상태의 기준 테스트 통과만으로 이 단계를 완료하지 않는다.

산출물: 데이터 목록·DDL·해시 보고서, 활성 코퍼스 구성표, 검색 기준선, 메타데이터 대응표.

완료 기준: 이전할 데이터와 실제 사용할 검색 데이터가 구분되고, 동일한 질문으로 이전 전 검색을 재현할 수 있다.

### 2단계 — MySQL 스키마·연결·원문 및 메타데이터 이전

작업:

- 대상 MySQL 버전·문자 인코딩·collation·드라이버를 확정하고 설정·연결·트랜잭션 계층을 추가한다. SQLite 연결을 일괄 문자열 치환하는 방식으로 처리하지 않는다.
- 기존 문서·법령·법령 버전·조문·판례·안내·청크와 관계 테이블을 보존한다. 판례 버전·관찰·별칭, 법령 원문 스냅샷·구조 테이블은 실제 입력 DB의 존재 여부에 따라 포함한다.
- 코퍼스를 식별하는 `corpus_id`와 자료 버전을 관리한다. 충돌하는 ID는 코퍼스 범위의 키·외래키로 분리하고 기존 검색용 `chunk_id`와 논리 조문 ID는 보존한다.
- 청크 검색 메타데이터를 저장할 구조를 추가한다. 필터·관계에 쓰는 값은 명시적 컬럼으로 관리하고, 재현에 필요한 확장 필드는 JSON 또는 관련 테이블에 보존한다. 중복 저장 필드의 기준 값과 검증 규칙을 정한다.
- 원문을 외부 파일 경로만으로 대체하지 않는다. 수집본이 있으면 본문·출처·수집 시각·해시를 저장하고, 정제 본문과 원수집본의 관계 및 완전성 상태를 기록한다.
- 부모·자식 순서의 배치 이전, 중복 실행, 오류 시 rollback·재개를 구현한다. 원본은 수정하지 않는다.
- 테이블별 건수·ID·본문·관계 및 필드 누락 여부를 비교한다. 긴 한글 본문·줄바꿈·빈 문자열·NULL·날짜·대소문자 ID·긴 URL을 포함한다.

산출물: MySQL 스키마·마이그레이션, 연결 설정, 이전·검증 도구, 실제 MySQL 검증 기록.

완료 기준: 실제 MySQL에서 원문·청크·출처·버전·이력의 누락과 설명되지 않은 내용 차이가 없고, 재실행해도 불필요한 행 증가가 없다.

### 3단계 — 청킹 → MySQL 저장 → 청크 내보내기

작업:

- 최초 이전 청크는 현재 검색 기준과 일치하도록 보존한다. 기존 청크 이전과 신규 원문 청킹 경로를 각각 제공한다.
- 법령은 조문·입력 항호 구조, 판례는 현재 활성 코퍼스의 공식 검색 대상 부분, 안내는 제목·문단 기준을 출발점으로 한다. 기존 `load_cases.py`가 `holding`을 검색 청크로 만드는 정책을 판례 전문 분할로 몰래 바꾸지 않는다.
- 자료별 입력·출력, 분할 기준·최대 길이·중첩 여부·청킹 버전·ID 생성 방식을 문서화한다. 현재 안내 600자 목표는 강제 최대 길이가 아니므로 긴 단일 문단 처리도 정의한다.
- 임베딩 토큰 제한으로 본문이 잘리는 자료를 점검하고, 분할 정책 변경이 필요하면 새 청킹 버전과 별도 검색 평가로 도입한다. 단순 추정 `token_count`를 실제 토크나이저 한도로 간주하지 않는다.
- 신규·수정·삭제를 문서 단위 트랜잭션으로 처리한다. 다른 코퍼스·자료 유형을 지우지 않고 기존 배포 버전은 복구 가능하게 보존한다.
- MySQL 조회로 기존 `chunk_id`, `doc_id`, `chunk_index`, `text`, `metadata` 형식을 생성한다. 출력 순서·필드 타입·NULL 변환을 명시한다.
- 출처 URL, 시행일·선고일, 현행 여부, 사건 식별자, 수집·버전 정보, 보완 페이지 해시 등을 보존한다.

산출물: MySQL 대응 적재·청킹·내보내기 코드, 유형별 규칙 문서, 재실행·갱신 검증.

완료 기준: 기존 JSONL을 입력에서 제외한 상태로 MySQL만 읽어 동일한 검색 ID·본문·필수 메타데이터를 재생성하고, 신규 자료도 청킹·저장·출력할 수 있다.

### 4단계 — BM25·Chroma 연결·갱신·팀 공유

작업:

- 일관된 DB 스냅샷에서 법령·민법·판례·안내 배포본을 생성한다. 코퍼스별 구성, 청크·메타데이터 해시, 모델 revision·차원, 청킹·검색 설정, 코드 버전을 manifest에 기록한다.
- 현재 채널별 BM25 구성과 법령·민법·판례 검색 프로필을 유지한다. SQLite 파일의 경로·해시 대신 새 배포본을 검증하는 계약을 추가한다. 기존 검증을 끄는 방식으로 연결하지 않는다.
- 같은 청크 ID·본문·모델로 Chroma를 생성한다. 기존 벡터 재사용 시 본문·전처리·모델·차원·메타데이터 호환성을 검사한다.
- 새 디렉터리에서 전체 색인과 검색 검증을 마친 후 배포 버전을 전환한다. 실행 중인 인덱스를 덮어쓰지 않는다.
- 서비스에 캐시된 BM25·모델·프로필의 전환 시점도 함께 처리한다. 파일만 교체하고 기존 프로세스가 옛 데이터를 계속 쓰는 상태를 방지한다.
- 배포본 설치·검증·현재 버전 조회·갱신·이전 버전 복구 명령을 제공한다. 잘못된 파일, 부분 다운로드, 모델 불일치, 인덱스 누락은 명확하게 실패시킨다.
- 팀 공유 위치와 MySQL 내부망 접속 방식을 확정하고, 비밀값 없는 설정 예시와 명령 순서를 작성한다.

산출물: 배포 manifest·생성/설치 도구, 리트리버 연결, 갱신·복구 절차, 팀원 실행 안내.

완료 기준: 별도 환경에서 같은 배포본과 모델을 설치해 ID·메타데이터·검색 설정 일치를 확인하고, 동일 질문의 검색 결과 차이를 허용오차·순위 동률 정책에 따라 검증한다. 갱신 실패 시 기존 버전으로 검색이 유지된다.

### 5단계 — 기존 LLM 연결·출처 추적·검색 회귀 검증

작업:

- `Evidence` / `RetrievalResult` 반환 계약과 `get_default_service()` → 앱 검색 라우팅 → `answer_question()` 흐름을 유지한다.
- 검색 본문·인용은 생성 문맥으로, 출처 URL은 결과·화면 출처로 전달되는지 확인한다. 생성 문맥에 URL이 반드시 포함된다고 가정하지 않는다.
- `corpus_id + release_id + chunk_id`에서 MySQL 문서·원문 버전까지 추적할 수 있게 한다. 기존 반환형을 불필요하게 깨지 않도록 응답 또는 추적 정보의 추가 방식을 정한다.
- 법령·판례·안내·민법·복합 질문과 근거 없음·LLM 오류를 검증한다. 기존 답변 보류·출처 검증을 유지한다.
- 동일 코퍼스·모델·평가셋·검색 설정으로 이전 전후 Hit@k·Recall@k·MRR, 유형별 결과와 지연시간을 비교한다. 정답이 없는 평가 문항은 별도 집계한다.
- 품질 허용 기준은 결과를 본 뒤 낮추지 않는다. 이전만 하는 경우 설명되지 않은 품질 저하를 허용하지 않고, 지연시간 허용치는 기준 측정 후 전환 전에 확정한다.
- Fake LLM으로 전달 계약을 검사하고, 실행 가능한 기존 Qwen 서버에서 실제 생성 및 앱 경로 검증을 별도로 수행한다. 단독 연결 스크립트 성공만으로 전체 앱 검증을 대체하지 않는다.

산출물: 이전 전후 평가 보고서, 실제 모델·버전·질문·검색 근거·입력 문맥·답변·출처 추적 기록, 팀원 재현 기록.

완료 기준: MySQL에서 나온 검색 데이터로 기존 앱·LLM이 동작하고, 사용한 출처를 DB 원문 버전까지 추적할 수 있으며, 검색 회귀와 실제 생성 검증이 통과한다.

## 5. 변경 위치와 작업 묶음

구현한 CLI는 `mysql_transfer`, `mysql_ingest`, `mysql_search`다. 실행법은 [원문 갱신 안내](../mysql-ingest.md)와 [검색 실행 안내](../mysql-search.md)를 따른다. 아래 표는 최초 작업 분류다.

| 묶음 | 변경 위치·작업 | 선행 조건 |
| --- | --- | --- |
| 기준선 | `server_sources.py`, `server_build.py`, 실제 DB/JSONL/프로필 조사·보고서 | 현재 작업 트리 보존 |
| DB | `src/database/config.py`, `relational.py`, MySQL 스키마·연결·마이그레이션 추가 | 데이터 목록·키 정책 확정 |
| 이전·적재 | `load_laws.py`, `load_cases.py`, `load_guides.py`, 판례 배포 입력 어댑터, 법령 구조 저장 호출부 | 실제 MySQL 초기화 |
| 검색 배포 | `knowledge_release.py`, `case_release.py`, `case_profile.py`, `profile.py`, `service.py`, `dense.py`, `index.py`, `setup_data.py` | MySQL 단독 내보내기 |

| 문서 | `.env.example`, README 관련 절, 상세 DB·팀 실행 문서 | 각 기능의 실제 실행 확인 |

PR 또는 리뷰 단위는 `기준선 → DB·이전 → 적재·청킹·내보내기 → 검색·배포 → LLM·검증`으로 나눈다. 문서는 각 변경과 함께 갱신한다. 일수는 데이터 재현·모델 실행·공용 DB 준비 시간을 확인한 뒤 산정한다.

## 6. 외부 환경과 역할 분담

구현 초기에 개발용 MySQL에서 기능을 검증하고, 공용 환경 준비 후 동일 스키마·배포 절차를 검증한다. 로컬 DB 성공만으로 공용 사용 완료를 표시하지 않는다.

공용 실행 전 필요한 정보:

- MySQL 호스트·포트·DB명, 네트워크 접근 방식, 읽기/적재 계정과 백업 책임자
- 팀 배포본 공유 위치와 버전 보존 정책
- 기존 Qwen을 실행할 LLM 서버 주소와 자원
- 팀원 재현을 확인할 별도 환경

비밀번호·API 키는 문서·Git·배포 manifest에 저장하지 않는다. 실제 접속값은 안전한 설정 경로로 제공한다. 해당 정보 없이도 스키마·적재·내보내기·단위 검증 작업은 진행할 수 있다.
