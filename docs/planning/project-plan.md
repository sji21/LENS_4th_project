# LENS 프로젝트 기획서

> 주택임대차 법령 근거 기반 전세계약 점검 RAG 질의응답 시스템  
> 기준 문서: `docs/planning/reference/source-project-plan.pdf`, 과정 공통 RAG 프로젝트 가이드라인  
> 작성 기준일: 2026-08-26

## 1. 프로젝트 한 줄 정의

예비 세입자와 세입자가 주택임대차 관련 질문을 하면 공공 법령·판례·정부 가이드에서 확인된 근거만 검색하여 답변하고, 선택적으로 등기사항증명서에서 계약 전 주의가 필요한 권리 신호를 찾아 추가 확인사항과 공식 근거를 안내하는 RAG 질의응답 서비스다. 시스템은 특정 주택의 안전 여부를 최종 판정하지 않으며 근거가 부족하거나 개별 법률 판단이 필요한 질문은 보류 또는 거절한다.

## 2. 문제 정의

### 2.1 해결하려는 문제

전세계약을 앞둔 사용자는 짧은 시간 안에 대항력, 우선변제권, 최우선변제, 근저당, 미납국세 확인, 보증금 반환보증, 임차권등기명령 같은 정보를 확인해야 한다. 하지만 관련 근거가 여러 법령과 시행령, 판례, 정부 가이드에 흩어져 있고 개정 시점에 따라 답이 달라질 수 있다.

일반 LLM은 다음 문제를 일으킬 수 있다.

- 학습 시점 이후 개정된 법령을 반영하지 못할 수 있다.
- 존재하지 않는 조문이나 출처를 생성할 수 있다.
- 개별 계약의 안전 여부를 충분한 데이터 없이 단정할 수 있다.
- 사용자가 답변을 직접 검증하기 어렵다.

LENS는 답변 범위를 넓히는 대신, 검색된 공공 문서로 확인할 수 있는 정보만 답하고 근거가 없으면 멈추는 것을 핵심 가치로 삼는다.

### 2.2 핵심 사용자

| 사용자 | 상황 | 핵심 요구 |
| --- | --- | --- |
| 1차 사용자 | 전세계약을 앞둔 예비 세입자 | 계약 전 확인 항목, 권리와 절차의 의미, 공식 확인 경로 |
| 2차 사용자 | 보증금 반환 문제를 겪는 세입자 | 임차권등기명령, 보증금 회수, 피해 지원 절차의 근거 |
| 보조 사용자 | 중개·상담 내용을 검증하려는 일반 사용자 | 설명의 법적 근거와 원문 링크 확인 |

### 2.3 성공 기준

사용자는 서비스에서 다음을 확인할 수 있어야 한다.

1. 질문과 관련된 법령·판례·정부 가이드 근거
2. 근거에 기반한 짧고 이해하기 쉬운 답변
3. 조문 번호, 문서명, 시행일 또는 발행일, 원문 링크
4. 실제로 검색된 근거 원문
5. 답변할 수 없는 이유와 다음 공식 확인 경로

## 3. 목표와 비목표

### 3.1 프로젝트 목표

- 공공 문서를 수집·정제하고 재현 가능한 문서 카탈로그를 구축한다.
- 조문과 문서 구조를 보존하는 청킹 전략을 구현한다.
- 질문과 관련된 근거를 검색하는 Dense Retrieval Baseline을 완성한다.
- 검색 근거에만 기반해 답변하고 출처를 결정론적으로 표시한다.
- 근거 부족, 범위 밖 질문, 개별 법률 판단 요청을 구분한다.
- 고정 평가셋으로 검색, 답변, 인용, 보류, 응답 시간을 측정한다.
- Streamlit에서 질문, 답변, 출처, 근거 원문을 확인할 수 있게 한다.

### 3.2 1차 MVP에서 하지 않는 것

- 특정 주택이 안전한지 또는 계약해도 되는지 최종 판정
- 소송 결과, 보증금 회수 가능성 같은 개별 사안 예측
- 임대인의 신용, 체납, 보증사고 이력 조회
- 부동산 시세 산정과 투자 추천
- 사용자 계약서·등기사항증명서 업로드
- 등기사항증명서 OCR과 이미지·멀티모달 처리
- 사용자별 권한, 장기 대화 이력, FastAPI 분리, GraphRAG, Fine-tuning

OCR은 별도 로컬 실험에서 가능성을 검토했지만 개인정보 유입과 문서 판독 오류의 책임이 커서 1차 Baseline에 포함하지 않는다. 기본 RAG와 안전장치가 평가를 통과한 이후, 별도의 개인정보 처리 정책과 실패 대응 기준을 적용한 2차 기능으로 구현한다.

### 3.3 단계별 제품 범위

| 단계 | 기능 | 사용자 가치 | 진입 조건 |
| --- | --- | --- | --- |
| 1차 MVP | 법령·판례·정부 가이드 기반 RAG 질문답변 | 권리와 절차를 공식 근거와 함께 이해 | 검색·인용·보류 평가 Gate 통과 |
| 2차 확장 | 등기사항증명서 업로드, 텍스트 추출, 위험 신호 점검 | 계약 전 확인이 필요한 권리를 놓치지 않도록 지원 | 개인정보·OCR·오판 대응 기준 합의 |
| 후속 확장 | 계약서 특약, 건축물대장 등 교차 점검 | 여러 문서 사이의 불일치와 추가 확인사항 안내 | 등기 점검 기능의 정밀도 검증 완료 |

2차 확장 기능의 목적은 `안전/위험` 이분법 판정이 아니다. 문서에서 확인된 사실을 `확인됨`, `주의 필요`, `판독 불가`로 구분하고 사용자가 추가로 확인할 항목을 제시하는 것이다.

## 4. 답변 범위 정책

모든 질문은 `ANSWER`, `ABSTAIN`, `REFUSE` 중 하나로 처리한다.

| 분류 | 조건 | 서비스 동작 | 예시 |
| --- | --- | --- | --- |
| ANSWER | 검색된 법령·판례·공식 가이드가 질문을 직접 뒷받침 | 근거 기반 답변, 출처, 기준일, 원문 링크 제공 | 전입신고와 확정일자의 차이는 무엇인가요? |
| ABSTAIN | 서비스 범위 안이지만 검색 근거가 부족하거나 상충 | 답변 보류, 부족한 근거 설명, 확인 경로 제시 | 제 계약서 특약의 효력이 검색 문서만으로 확인되지 않아요 |
| REFUSE | 개별 법률 판단, 결과 예측, 개인정보 조회 또는 타 도메인 | 범위 밖 사유와 공적 상담 창구 안내 | 이 집과 계약해도 안전한가요? |

### 4.1 답변 원칙

- 검색되지 않은 조문이나 출처를 답변에 추가하지 않는다.
- 출처 블록은 LLM이 아니라 코드가 검색 결과 메타데이터로 생성한다.
- 답변의 인용 조문이 검색 컨텍스트에 없으면 해당 문장을 제거하거나 1회 재생성한다.
- 법령의 시행일, 효력 상태, 한시법 만료일을 답변에 함께 표시한다.
- 답변 하단에 법률자문이 아니라는 고정 고지를 코드로 삽입한다.
- 근거가 없다는 것은 시스템 실패가 아니라 정상적인 보류 결과다.

### 4.2 등기사항증명서 점검 결과 원칙

등기 점검 결과도 최종 답변 상태는 `ANSWER`, `ABSTAIN`, `REFUSE` 정책을 따른다. 문서 안에서 개별 추출 항목은 다음처럼 표시한다.

| 표시 | 의미 | 출력 방식 |
| --- | --- | --- |
| 확인됨 | 문서에서 권리나 사실이 명확하게 판독됨 | 원문 문구, 문서 구역, 관련 근거 표시 |
| 주의 필요 | 계약 전 금액·순위·말소 여부 등을 추가 확인해야 하는 권리가 발견됨 | 발견 사실과 확인 질문을 함께 제시 |
| 판독 불가 | OCR 결과가 불명확하거나 방식 간 결과가 충돌 | 추측하지 않고 재업로드·원본 확인 요청 |

서비스는 “이 집은 안전합니다” 또는 “계약하면 안 됩니다”라고 결론 내리지 않는다. 대신 “을구에서 근저당권이 확인됐으므로 채권최고액, 실제 채무액, 선순위 권리, 주택 시세를 추가 확인해야 합니다”처럼 관찰 사실과 다음 행동을 분리해 안내한다.

## 5. 데이터 범위

### 5.1 1차 문서 범위

| 축 | 문서 범위 | 주요 질문 |
| --- | --- | --- |
| 임대차 본체 | 주택임대차보호법, 시행령·시행규칙, 관련 민법 조문 | 대항력, 우선변제, 계약 갱신, 증액, 최우선변제 |
| 등기·권리·조세 | 부동산등기 관련 법령, 민사집행 관련 법령, 국세·지방세 관련 법령 | 근저당, 권리 순서, 배당, 미납세금 확인 절차 |
| 계약·중개 | 공인중개사 관련 법령, 임대차 신고 관련 법령, 표준계약서·확인설명서 | 중개사의 설명 의무, 신고, 계약 단계 점검 |
| 사후 구제 | 전세사기 피해 지원 관련 법령, 임차권등기명령·경매·배당 관련 문서 | 보증금 미반환 시 대응과 지원 절차 |
| 공식 가이드 | 국토교통부, 전세피해지원 관련 기관의 가이드와 체크리스트 | 계약 전·중·후 실무 점검 |

구체적인 법령 효력과 시행일은 문서에 하드코딩하지 않고 수집 시점의 공식 API 응답으로 검증한다.

### 5.2 수집 원칙

- 법령과 판례는 공식 API 또는 공식 원문 페이지에서 수집한다.
- 정부 가이드는 공식 기관이 발행한 PDF·HTML만 사용한다.
- 원문 파일은 `data/raw/`에 저장하고 Git에는 커밋하지 않는다.
- 수집 이력, URL, 수집일, 해시, 라이선스, 파싱 상태는 `data/manifest.jsonl`에 커밋한다.
- 폐지·연혁 문서는 삭제하지 않되 기본 검색에서는 제외한다.
- 판례 전문은 과도한 노이즈를 피하기 위해 판시사항과 판결요지를 우선 청킹한다.

### 5.3 필수 메타데이터

```json
{
  "doc_id": "문서 고유 ID",
  "chunk_id": "청크 고유 ID",
  "title": "문서명",
  "doc_type": "law | decree | rule | precedent | interp | guide",
  "article_no": "조문 번호",
  "source_url": "공식 원문 URL",
  "effective_date": "시행일",
  "expiry_date": "한시법 만료일 또는 빈 문자열",
  "published_at": "가이드 발행일",
  "status": "현행 | 연혁 | 폐지",
  "version": "공포번호 또는 문서 버전",
  "checksum": "원문 해시",
  "refs": "참조 조문 ID를 | 로 연결한 문자열"
}
```

Vector DB 메타데이터에는 문자열·숫자·불리언 스칼라만 저장하고 `None`과 배열은 직렬화한다.

| 검색 | Dense Top-k와 현행·기준일 필터 | 대표 질문의 정답 근거가 상위 결과에 포함 |

| 안전장치 | ANSWER/ABSTAIN/REFUSE, PII 마스킹, 인젝션 방어 | 적대적 질문에서 범위 정책 준수 |
| 평가 | Dev/Holdout, 검색·답변·인용·보류·지연 지표 | Baseline과 실험 결과 JSON 저장 |
| 서비스 | Streamlit 질문·답변·출처·근거 화면 | 새 환경에서 README만으로 실행 가능 |

### 6.1 2차 등기 점검 확장 범위

| 영역 | 구현 내용 | 완료 기준 |
| --- | --- | --- |
| 업로드 | PDF만 허용하고 크기·페이지 수·MIME 유형 검증 | 비정상 파일을 처리 전에 차단 |
| 텍스트 추출 | PDF 내장 텍스트와 Tesseract OCR을 병렬 실행 | macOS·Windows에서 같은 명령으로 실행 가능 |
| 선택적 보강 | 두 로컬 결과가 충돌하거나 판독 불가인 페이지만 OpenAI Vision 사용 | 전체 문서 API 전송을 기본값으로 사용하지 않음 |
| 개인정보 | 이름·주민등록번호·주소 일부를 LLM 호출과 로그 저장 전에 마스킹 | 원본과 추출문을 세션 종료 후 삭제 |
| 구조화 | 갑구·을구와 권리 항목을 스키마로 변환하고 원문 위치 보존 | 추출값마다 페이지·구역·근거 문구 확인 가능 |
| 위험 신호 | 규칙 기반 탐지 후 관련 법령·가이드 RAG 검색 | 발견 사실과 추가 확인사항을 함께 출력 |
| 불일치 처리 | 추출 방식 간 결과가 다르면 신뢰도를 낮추고 판독 불가 처리 | 임의 선택이나 값 합성 없음 |
| 평가 | 필드 단위 정밀도·재현율, 위험 신호 Recall, 처리시간·비용 측정 | 고정 등기 샘플로 방식별·병렬 결과 비교 |

### 6.2 등기사항증명서 주요 점검 항목

| 문서 구역 | 점검 신호 | 사용자에게 안내할 추가 확인사항 |
| --- | --- | --- |
| 표제부 | 주소·동호수·건물 유형 불일치 | 계약 대상과 등기 표시가 같은지 확인 |
| 갑구 | 소유자 불일치, 신탁등기, 압류·가압류·가처분, 경매개시결정 | 계약 상대방 권한과 처분 제한 상태 확인 |
| 을구 | 근저당권·저당권, 전세권, 임차권등기, 공동담보 | 채권최고액, 실제 채무액, 순위, 말소 조건 확인 |
| 변경 이력 | 짧은 기간의 잦은 소유권 이전 또는 권리 변동 | 변동 원인과 최신 등기 여부 확인 |
| 문서 상태 | 오래된 발급일, 말소 표시 불명확, OCR 충돌 | 계약 직전 최신 원본을 다시 발급하여 확인 |

임차권등기는 존재 여부와 말소 여부를 우선 확인하며 접수번호 자체는 핵심 추출값으로 요구하지 않는다. 사람 이름도 위험 신호 판단에 필요한 `소유자와 계약 상대방의 일치 여부` 확인용으로만 처리하고 결과 화면과 로그에서는 최소한으로 노출한다.

```text
        |
```

### 7.3 등기 점검 단계

```text
등기사항증명서 PDF 업로드
   |
   v
파일 검증 + 세션 임시 저장
   |
   +---- PDF 내장 텍스트 추출 --------+
   |                                  |
   +---- Tesseract 페이지 병렬 OCR ----+---- 결과 정규화·교차 검증
                                           |
                                           +---- 충돌 페이지 선택적 Vision 보강
                                           v
                                  PII 마스킹 + 갑구·을구 구조화
                                           |
                                           v
                                  위험 신호 규칙 탐지
                                           |
                                           v
                                  관련 법령·가이드 RAG 검색
                                           |
                                           v
```

병렬 처리는 한 PDF의 페이지별 OCR과 내장 텍스트 추출을 동시에 수행해 응답 시간을 줄이는 용도다. 여러 방식의 결과가 같을 때 신뢰도를 높이고, 다를 때는 자동으로 단정하지 않고 검토 대상으로 표시한다.

### 7.4 평가 단계

```text

   -> 검색·답변·인용·보류·지연 측정
   -> 실패 qid 분석
   -> 한 가지 조건만 변경
   -> 재실행·비교
   -> 최종 설정 확정

```

## 9. 검색과 생성 정책

### 9.1 Baseline 설정

- 청킹: 조 1개를 청크 1개로 사용
- 장문 기준: 1,000토큰 초과 시 항 단위 분할
- 짧은 조문: 인접 조문과 합치지 않음
- 검색: Dense Top-k, 초기 `k=5`
- 기본 필터: 질문 기준일에 효력이 있는 문서, `status=현행`
- 생성 온도: 0
- 컨텍스트: 검색된 청크와 메타데이터만 전달
- 출처: 코드가 `title`, `article_no`, `effective_date`, `source_url`로 생성

### 9.2 조건부 개선 순서

한 실험에서는 한 가지 조건만 변경한다.

| 순서 | 개선 후보 | 착수 조건 |
| --- | --- | --- |
| E1 | 효력·기준일 메타데이터 필터 보강 | 폐지·미시행 조문 오검색 발생 |
| E2 | BM25 + Dense Hybrid와 RRF | 조문번호·고유명사 질문 Hit@5 미달 |
| E3 | Cross-encoder Reranker | 정답은 검색되지만 Top-3 정밀도가 낮음 |
| E4 | 참조 조문 1-hop 확장 | 단일 조문만으로 답변이 불완전한 실패가 반복 |
| E5 | LangGraph 라우팅과 1회 재검색 | 단일 체인으로 보류 정확도가 개선되지 않음 |

평가 실패 사례가 필요성을 입증하지 못한 기능은 구현하지 않는다.

## 10. 안전과 보안

| 위험 | 방어 방식 |
| --- | --- |
| 근거 없는 답변 | 유사도·근거 충분성 임계값 미달 시 ABSTAIN |
| 존재하지 않는 출처 | 검색 chunk의 조문 집합과 답변 인용을 코드로 비교 |
| 폐지·미시행 법령 | status, effective_date, expiry_date 필터 |
| 개별 법률 판단 | 범위 분류에서 REFUSE하고 공적 상담 창구 안내 |
| 프롬프트 인젝션 | 검색 문서를 명령이 아닌 데이터로 취급하고 시스템 지시 우선 |
| 개인정보 입력 | 주민등록번호·전화번호 패턴을 임베딩·LLM 호출 전에 마스킹 |
| 비밀정보 노출 | `.env`와 원문 데이터를 Git에서 제외, 로그에 키·원문 미기록 |
| 과거 대화 오염 | MVP에서는 장기 대화 메모리를 사용하지 않음 |

## 11. 평가 계획

### 11.1 평가셋

| 세트 | 규모 | 구성 | 사용 규칙 |
| --- | ---: | --- | --- |
| Dev | 60 | answerable 40, unanswerable 10, out_of_scope 10 | Gate 2-5에서 반복 사용 |
| Holdout | 25 | Dev와 유사한 비율 | Gate 1에서 작성·봉인 후 Gate 6에서 1회 사용 |
| 적대적 | 20 | 폐지 조문, 도메인 혼동, 법률판단 유도, 인젝션, 허위 조문 | Gate 4 안전성 평가 |

평가 문항에는 `gold_articles`, `gold_chunk_ids`, `reference_answer`, `answer_type`, 작성자와 검증자를 기록한다.

### 11.2 지표

| 대상 | 지표 | 판정 방법 |
| --- | --- | --- |
| 검색 | Hit@5, MRR | gold 조문·청크가 검색 순위에 포함되는지 자동 채점 |
| 답변 | Faithfulness, Answer Relevancy | 검색 근거 충실도와 질문 관련성 측정 |
| 인용 | Citation Precision | 표시된 출처 중 검색 컨텍스트에 실제 존재하는 비율 |
| 보류 | Abstain Accuracy | unanswerable에서 올바르게 보류한 비율 |
| 거절 | Refusal Accuracy | out_of_scope에서 올바르게 거절한 비율 |
| 과잉 보류 | False Abstain Rate | answerable 질문을 잘못 보류한 비율 |
| 운영 | p50/p95, 오류율 | 검색과 생성 단계 시간을 분리 기록 |

### 11.3 잠정 통과 목표

팀은 Gate 1 종료 전에 목표값을 확정하고 이후 변경하지 않는다.

| 지표 | 잠정 목표 |
| --- | ---: |
| Hit@5 | 0.80 이상 |
| MRR | 0.65 이상 |
| Citation Precision | 0.95 이상 |
| Abstain Accuracy | 0.85 이상 |
| Refusal Accuracy | 0.90 이상 |
| 오류율 | 1% 미만 |
| 응답시간 | p95 10초 이하 |

### 11.4 실험 기록 형식

| 실험 | 변경 조건 | Hit@5 | MRR | Citation Precision | 보류 정확도 | p50 | 실패 qid | 해석 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | --- | --- |
| Baseline | 조 단위, Dense, k=5 | | | | | | | |
| Exp 1 | 한 가지 조건 변경 | | | | | | | |
| Final | 채택 설정 | | | | | | | |
| Holdout | Final 설정 1회 | | | | | | | |

`run_eval.py`는 `changed`에 하나의 키만 허용해 한 실험에 한 조건 원칙을 코드로 강제한다.

### 11.5 등기 점검 평가

전체 OCR 문자 정확도보다 서비스에 필요한 위험 신호를 놓치지 않는지를 우선 평가한다.

| 평가 대상 | 지표 | 확인 내용 |
| --- | --- | --- |
| 구역 분리 | 갑구·을구 분류 정확도 | 권리 항목이 올바른 구역에 연결되는가 |
| 핵심 필드 | Field Precision·Recall·F1 | 권리 종류, 금액, 설정·말소 상태를 정확히 추출하는가 |
| 위험 탐지 | Risk Signal Recall | 근저당·신탁·압류·임차권등기 등 주의 신호를 놓치지 않는가 |
| 과잉 경고 | False Positive Rate | 존재하지 않는 권리를 위험 신호로 표시하지 않는가 |
| 불일치 | Abstain Accuracy | 방식 간 충돌과 저신뢰 결과를 올바르게 판독 불가 처리하는가 |
| 운영 | 페이지당 시간, 전체 p95, API 비용 | 순차·병렬·선택적 API 방식의 효율 차이 |

비교 실험은 `내장 텍스트`, `Tesseract`, `선택적 Vision`, `내장 텍스트 + Tesseract 병렬 교차 검증`을 동일한 샘플과 정답 라벨로 평가한다. 이름과 접수번호 같은 비핵심 항목은 종합 위험 신호 점수에서 제외한다.

| --- | --- | --- |
| E-D1 | 업로드 보안, 개인정보 정책, 정답 라벨 스키마 확정 | 위협 모델, 등기 평가셋 |
| E-D2 | 내장 텍스트·Tesseract 병렬 추출, 갑구·을구 구조화 | 추출 파이프라인 |
| E-D3 | 위험 신호 규칙, RAG 근거 연결, 선택적 Vision 보강 | 등기 점검 데모 |
| E-D4 | 방식별 정확도·시간·비용 비교, 실패 사례 분석 | 비교 보고서, 최종 설정 |

## 14. 저장소 적용 계획

| 경로 | 현재 상태 | 다음 구현 |
| --- | --- | --- |
| `app/streamlit_app.py` | 진입점 docstring | 질문·답변·출처·근거 4영역 UI |
| `src/ingestion/` | 파일 골격 | API 수집, XML/PDF 파싱, 조 단위 청킹 |
| `src/retrieval/` | 파일 골격 | Chroma index, Dense retriever, 기준일 필터 |
| `src/generation/` | 파일 골격 | 범위 정책, LCEL, 인용 생성·검증 |
| `src/evaluation/` | 파일 골격 | Hit@k, MRR, CitPrec, 보류·거절, 실험 비교 |
| `data/eval/` | 빈 파일 | Dev 60과 봉인 Holdout 25 작성 |
| `data/manifest.jsonl` | 빈 파일 | 수집 문서 추적 레코드 작성 |
| `docs/document-card.md` | 템플릿 | Gate 1 실측값과 라이선스 기록 |
| `docs/corpus-audit.md` | 템플릿 | 추출률·중복·깨진 문자·근거 존재 여부 기록 |
| `tests/` | 빈 골격 | 파서·청커·인용·지표·범위 정책 테스트 |

2차 확장 시 `src/document_check/`에 업로드 검증, OCR, 구조화, 위험 신호 규칙을 분리하고 `tests/document_check/`에 운영체제 독립적인 테스트 픽스처를 둔다. Tesseract 실행 파일 경로는 코드에 하드코딩하지 않고 환경 변수와 자동 탐색으로 처리한다.

현재 저장소는 스캐폴드 상태다. 이 문서가 승인되면 G1 데이터 수집과 평가셋 설계를 병렬로 시작한다.

## 15. 리스크와 중단 기준

| 리스크 | 대응 | 중단·축소 기준 |
| --- | --- | --- |
| 공식 API 승인 지연 | 가장 먼저 신청하고 공식 HTML 대체 경로 검토 | D2까지 미승인 시 법령 범위를 핵심 8건으로 축소 |
| PDF·표 파싱 실패 | 해당 표만 검증된 JSON으로 수동 구조화 | 자동 추출률 80% 미만 문서는 Baseline corpus에서 제외 |
| 정답 근거가 corpus에 없음 | 질문을 unanswerable로 재분류 | 근거 없이 reference answer를 유지하지 않음 |
| Baseline 검색 성능 부족 | k, 청킹, 필터를 순차적으로 실험 | D6까지 baseline run이 없으면 확장 기능 전부 중단 |
| LLM 비용 초과 | 검색 평가는 LLM 없이 반복하고 생성 평가 횟수 제한 | 예산 한도 도달 시 RAGAS 평가 표본 축소 |
| 법령 개정 | corpus 스냅샷과 기준일 표시, 재수집 로그 유지 | 버전 확인이 안 되는 문서는 답변 근거에서 제외 |
| 답변 보류가 너무 많음 | 실패 유형을 분석하고 검색·임계값 중 하나만 변경 | 근거 없는 답변을 늘리는 방향으로 완화하지 않음 |
| OCR 오인식·권리 누락 | 핵심 키워드 다중 방식 교차 검증과 저신뢰 보류 | 위험 신호 Recall 목표 미달 시 사용자 기능 비공개 |
| 개인정보 유출 | 세션 임시 처리, PII 마스킹, 원문·추출문 자동 삭제 | 삭제 검증과 로그 비식별화가 안 되면 업로드 중단 |
| 운영체제 차이 | macOS·Windows CI와 Tesseract 자동 탐색 | 한 운영체제에서 재현되지 않으면 2차 기능 출시 보류 |
| 잘못된 안전 인식 | 안전 점수·계약 추천 금지, 확인사항 중심 UI | 단정 표현 회귀 테스트 실패 시 배포 중단 |
