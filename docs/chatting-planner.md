# PATCH-031 · Qwen 대화 판단

개발 실험 정리일: 2026-09-13. 아래 01~12는 개발용 후보 비교 기록이며 최종 수용평가가 아니다.

기존 Qwen3-8B Q4와 Ollama를 사용해 한 번의 호출에서 사용자 진술과 대화 진행 방향을 제안한다.
서버는 출처 검사를 통과한 사용자 진술과 현재 입력으로 검색문을 조립한다. 별도 모델이나 다중
에이전트를 추가하지 않는다. 결과는 PATCH-030의 계약으로 검사한 뒤 반환하며 이 모듈 자체는
상태를 저장하거나 검색·법률 답변을 실행하지 않는다.

## 모델과 입력

`chat/dialogue_planner.py`는 SystemMessage에 판단 규칙, HumanMessage에 사용자 자료 JSON을
넣는다. 모델 입력은 현재 상태의 허용된 필드로 제한한다. 평가 라벨·문서 원문·거절/보류된 생성문을
전달하지 않으며 사용자 기억은 선택적 외부 추적에도 보내지 않는다. 시스템 규칙을 바꾸라는 문서나
사용자 문구를 지시가 아닌 자료로 다루도록 명시한다. 이것만으로 모든 공격 방어를 보장하지 않으며
실행 전 공통 입력 보호는 PATCH-032에서 적용한다.

Ollama의 [`format` JSON Schema](https://docs.ollama.com/capabilities/structured-outputs)를
native `/api/chat` 최상위에 전달한다. 형식 설정이 없는 기존 생성 요청의 동작은 유지한다.
판단 요청은 temperature 0, think false, 최대 768 토큰, context 8192, timeout 35초다.
`allow_route_fallback=False`로 선택된 서버의 생성 실패 후 다른 서버에서 재생성하지 않는다.
서버 준비 단계의 경로 선택은 기존 설정을 사용한다. 형식 오류를 고치는 두 번째 모델 호출은 없다.

## 원시 출력과 실행 계약

현재 원시 모델 출력은 아래 7개 항목만 요구한다. 모델은 검색문과 확인 질문의 문장을 작성하지 않는다.

| 모델 출력 | 역할 |
| --- | --- |
| `statements` | 현재 발화의 명시적 진술. `[{field, value, evidence}]` 배열이며 새 진술이 없으면 `[]` |
| `intent` | 인사·질문·후속 요청·정정·확인 답변·쉬운 설명·주제 전환·문서 질문 분류 |
| `topic` | 현재 상담의 주제 또는 `null` |
| `action` | `social`, `clarify`, `rag`, `refuse` 중 다음 행동 |
| `clarify_field` | 확인이 필요한 사실 항목·상세 상황·문서 선택 또는 `null` |
| `document_id` | 현재 세션이 소유한 문서 ID 또는 `null` |
| `style` | 기본·쉬운 설명·간단한 설명 방식 |

`expand_proposal`은 이 7개 항목을 기존 10개 항목의 내부 실행 계약으로 변환한다. `statements`를
`updates`로 옮기고, `topic_changed`는 의도가 `topic_change`일 때만 `true`로 계산한다.
`question`은 `null`로 두며, 실제 확인 질문은 PATCH-033의 서버 동작에서 구성할 예정이다.
`search_query`는 RAG 행동일 때 우선 현재 사용자 입력으로 채운다. 모델이 이 내부 필드를 추가하거나
필수 항목을 누락하면 거절하며, 중복 JSON 키도 허용하지 않는다.

진술 배열은 출처·값 검사 후 `{field: {value, evidence}}` 형태로 기존 `Decision`에 전달한다.
PATCH-030의 10개 항목과 기본 객체 계약은 유지하며 모델 연결부에서만 배열 변환을 허용한다.
중복 field, 미등록 항목, 추가 키, 잘못된 값, 인용 출처와 숫자·부정 검사도 계속 적용한다.

### 서버의 검색문 구성

`chat/dialogue_query.py`는 검사된 판단을 복사한 상태에 적용해 최신 사실만 조립한다. 선택 문서의
고정 종류명, 활성 주제와 사용자 진술의 항목별 값, 현재 사용자 입력 전체를 검색문에 넣는다.
정정된 값은 이전 값을 대체하고, 명시적인 상담 대상 전환은 이전 사실과 선택 문서를 제외한다.
문서 원문·파일명·원시 답변·변경 감사 이력을 검색문으로 복사하지 않으며, 저장된 사용자 진술을
법적으로 확인된 사실로 취급하지 않는다. RAG 이외 행동의 검색문은 빈 문자열이다.

현재 입력을 모델이 다시 요약하거나 다른 질문으로 바꾸지 않으므로, 질문의 조건을 삭제하거나
종료 여부를 반환 여부로 바꾸는 재작성 오류를 줄이는 구조다. 사실 추출의 누락 자체를 해결하는
장치는 아니며, 검색의 적합성도 별도 검증해야 한다. 이 단계는 추가 LLM 호출 없이 수행되고,
조립한 결과는 내부 계약을 다시 통과해야 한다. 길이 한도 등으로 실패하면 원래 세션 상태를 바꾸지 않는다.

원문 보존 경로는 현재 입력이 검색문 끝에 그대로 있는지 확인하고, 추가된 문맥의 부정·긍정만 검사한다.
사용자가 가정으로 묻는 문장을 확정된 진술로 오인하지 않기 위한 구분이다. 숫자는 검색문 전체에서
검사하며, 진술의 값·인용 검사는 유지한다. 일반 계약 파서는 원문 보존 옵션을 기본으로 허용하지 않는다.

현재 입력을 `user`, 이전 자료를 `context`로 구분한다. 이전 사실은 값만 전달하여 과거 인용을
현재 인용으로 복사하는 혼동을 줄인다. 저장 상태에는 원문 출처와 변경 이력을 계속 보존한다.

모델은 예시와 상태를 바탕으로 표현을 판단한다. 발화 문장을 조건문으로 나열하지 않는다.
인사가 섞인 실제 질문, 단답의 대기 항목 연결, 명시적 상담 대상 변경, 쉬운 설명의 RAG 연결을
예시로 안내한다. 현재는 완성된 입력·출력 JSON 예시를 SystemMessage 안에 서로 독립된 설명으로
넣고, 실제 상담 자료는 마지막 HumanMessage 하나에만 전달한다. 시스템 설명에는 예시의 사실을
재사용하지 말고 실제 Human JSON의 문맥만 사용하도록 명시한다. 예시를 실제 사용자·AI 메시지로
대화 이력에 추가하던 07의 방식은 채택하지 않는다. 프롬프트 조정에는 개발용 자료만 사용하고
최종 수용평가 본문은 열람하지 않았다.

### 모델 오류와 파서 오류 구분

08의 `DEV-004/1`, `DEV-006/1`은 원시 제안에 계약 종료 `예`와 보증금 반환 `아니요`가 함께
들어 있다. 그런데 인용한 복합절 전체에 있는 `못 받았다`를 계약 종료의 부정으로 해석해 파서가
거절했다. 이는 모델이 종료 여부를 뒤집었다는 증거가 아니라, 서로 다른 사실의 부정 범위를 구분하지
못한 파서 오류다. 원시 `polarity` 오류와 실패 점수는 그대로 보존하고 수동 원인 판정을 분리한다.

09는 같은 프롬프트와 부정 범위 수정으로 [23턴 전체](../data/eval/chatting/results/planner-dev-09.json)를
실행했다. 행동 22/23, 의도 16/23, 필수 사실 16/17, 검색 필수 표현 21/21, 검색 금지 표현 제외
9/9였다. 원시 출력 계약 오류 1턴 때문에 `complete=false`이며 품질 완료 결과로 사용하지 않는다.
판단 지연 p50은 5.711초, p95는 9.792초였고 모델 호출은 23회였다.

남은 계약 오류는 현재 사용자가 말하지 않은 과거의 `월세`를 같은 값의 새 update로 반복한 것이다.
또한 다른 계약으로 전환한 한 턴에서 계약 종류를 누락하고 `property_type=보일러`를 생성했다.
의도 라벨은 새 질문과 같은 상담의 후속 질문을 혼동했지만, 해당 검색문들은 앞선 주제를 유지했다.
이후 변경에서는 이런 모델의 실수를 원시 기록과 별도로 관측한다.

### 10~11 전체 개발 실험

10·11은 모두 모델이 검색문까지 제안하던 10개 출력 항목의 실험이다. 위의 현재 7개 항목 설계에

11은 모든 턴이 실행됐지만, 종료·미반환 진술의 초기 누락이 정정과 후속 요청까지 이어졌다.
다른 상담에서도 미반환 진술을 누락했고 주제 전환에서 월세 종류를 저장하지 않았다. 이 때문에

단순한 단어 일치의 거짓 실패로 처리하지 않는다. 검색 금지 표현은 관측된 10턴에서 통과했다.

11의 `complete=true`는 기술적 실행 완료만 뜻한다. 사실 보존과 질문 관련성의 문제가 남았으므로
품질 완료로 보지 않는다. 후속 7개 항목 설계에서는 모델의 진술 추출·행동 판단과 서버의 검색문
조립을 분리하며, 해당 설계는 독립된 실행 결과로 검증해야 한다.

### 12 · 7개 출력 항목과 서버 검색문

[12차 전체 결과](../data/eval/chatting/results/planner-dev-12.json)는 23턴을 실행했고 코드·모델은
실행 도중 변경되지 않았다. 실행 오류가 3턴 있어 `complete=false`다. 이후 인용 검사와 원문 보존
검사를 수정한 현재 코드의 검증 결과로 소급해서 사용하지 않는다. 13차의 별도 개발 표본 결과는 아래에 구분한다.

| 원시 계약 통과 | 원시 의도 | 실행 의도 | 행동 | 필수 사실 | 정규화 발생 턴 | 지연 p50 / p95 | 모델 호출 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 19/23 | 16/23 | 19/23 | 20/23 | 17/17 | 4/23 | 5.821초 / 8.526초 | 23회 |

실행 의도는 19턴 통과·1턴 오분류·3턴 오류로 관측되지 않음이다. 필수 사실 17/17은 각 턴에서
보이는 누적 상태에 필요한 값이 있는지를 측정한다. 모든 발화의 추출이나 출처가 적절했다는 뜻은
아니다. 실제로 정정 턴의 월세 값은 맞았지만 그 근거를 `정정할게요`로 제안했고 당시 검사를 통과했다.

실행 오류 3턴은 다음과 같다. 후속 서류 요청에서 이전 월세 진술을 현재 발화처럼 복사하고 주제도
바꾸어 출처 검사에 실패했다. 문서에 적힌 금액을 묻는 질문에서는 금액의 `모름`을 새 진술로
만들었다. 기한을 묻는 질문에서도 날짜의 `모름`을 새 진술로 만들었다. 두 질문은 문자 그대로의
금액·날짜를 제시하지 않아 값 검사에서 거절됐다. 별도로 근거를 요청한 턴을 `document_question`으로
분류했고 `관련된`을 상담 대상으로 저장했다. 인용 문자열의 존재만으로 그 의미까지 입증되지는 않는다.

검색 필수 표현은 19턴 통과·4턴 관측되지 않음이었다. 검색 금지 표현은 7턴 통과·1턴 실패·15턴
관측되지 않음이었다. 금지 표현의 실패는 정정문 안의 부정된 이전 계약 종류까지 원문으로 보존한
결과다. 해당 검색문의 활성 계약 항목은 월세였고, 전세는 사용자 입력의 `전세가 아니라` 안에만
남았다. 단어 검사 결과는 실패 그대로 보존하고, 수동 검토에서는 이전 값을 활성 사실로 되살린
문제와 구분한다. 다만 같은 턴의 부적절한 인용 출처까지 정상으로 판정하지 않는다.

12차 이후 계약 종류의 인용이 실제 값을 포함해야 한다는 검사를 강화했고, 원문 보존 경로에서는
가정 질문과 서버가 추가한 사실 문맥을 구분한다. 질문을 미지의 사실로 저장하지 않고 같은 상담의
주제를 유지하도록 프롬프트도 조정했다. 이 변경의 효과는 후속 실행에서 따로 확인한다.

### 실행 전 정합성 검사

- 역할과 건물 종류는 허용 값과 실제 인용을 함께 검사한다. 수리 대상인 보일러를 건물 종류로
  저장하거나 월세라는 이유만으로 화자를 임차인이라고 단정하지 않는다. 주체는 원문 표현을 보존한다.
- 모델이 이미 활성화된 동일 진술을 과거 출처로 다시 제안한 경우, 조건을 엄격하게 확인해 해당
  중복 update를 실행 목록에서만 제외할 수 있다. 값·주제가 같고 기존 사용자 진술의 출처에 정확히
  포함된 인용이어야 한다. 정정·주제 전환에서는 사용하지 않는다. 원래 출처와 진술 시점은 유지하며
  현재 사용자가 새로 말했다고 기록하지 않는다. 다른 잘못된 값·문서·인용은 계속 거절한다.
- 소유 문서 선택과 현재 상담 주제처럼 이미 구조화된 관계로 의도 라벨의 정합성을 맞춘다.
  같은 주제의 후속 요청이나 대기 질문이 없는 상태의 잘못된 `clarification_answer` 라벨을 구분하며,
  행동·검색 질문·사용자 사실을 이 과정에서 바꾸지 않는다. 사용하지 않는 확인 질문 필드는 제거한다.
- `raw_output_valid`, `raw_intent_check`, `normalizations`와 원시 제안을 함께 기록한다. 실행 계약의
  최종 의도 점수와 모델이 처음 출력한 의도 점수를 분리하며, 정규화를 모델의 원래 정답으로 세지 않는다.

이 규칙은 모델이 놓친 모든 사실이나 주제 전환을 찾아내는 한국어 의미 분석기가 아니다. 변경 값,
정정 또는 주제 전환의 잘못된 출처를 기존 사실이라는 이유로 허용하지 않는다. 사용자 원문과 실제
검색 질문의 수동 대조 및 후속 통합 검증은 계속 필요하다.

### 결과 보존과 소스 반영 경계

각 실행의 원시 제안, 전후 상태, 오류, 코드·모델 해시와 중단 사유를 차수별 파일로 보존한다.
실패 기록을 지우거나 평가 라벨을 바꿔 점수를 올리지 않는다. 출력이 형식 검사를 통과하더라도
사용자 진술 누락, 불필요한 추정, 검색 질문의 대상 변경은 별도로 검토한다.

01~12는 PATCH-031 작업 브랜치에서 교체·검토한 후보 설정이다. 결과 파일을 보존하는 것은 과거
프롬프트·nullable 형식·추론 활성화·Human/AI 예시 방식을 운영 코드에 모두 누적하거나, 각 후보를
완료한 기능 패치로 병합한다는 뜻이 아니다. 최종 소스는 관련 테스트와 실제 모델 검증을 거쳐 별도로
확정해야 한다. `chatting-upgrade` 통합과 전체 수용평가 완료도 구분하며, `main` 병합·원격 푸시는
별도 요청 범위다.

## PATCH-031 연결부 검증과 남은 통합 검증

[13차 표본](../data/eval/chatting/results/planner-dev-13-sample.json)은 정정·문서·기한 8턴 중 6턴의 판단을 수용하고 2턴을 출처·값 검사에서 거절했다. 정정과 후속 서류 질문은 연결됐지만 문서 금액 질문과 기한 질문의 잘못된 진술 제안이 남았다. 원시 실패를 정상 판단으로 바꾸지 않았고 상태를 변경하지 않았다. 이 표본은 전체 평가 통과가 아니다.

단위·기존 회귀 검사는 1,276개 및 137개 subtest가 통과했다. 선택적 LangSmith 2개와 개인 PDF 1개는 환경 자료가 없어 제외했다. 판단 연결부는 허용된 제안만 반환하고 나머지는 PlanningError로 종료하는 계약까지 검증했다. PATCH-032에서 이 실패를 기존 경로로 연결하며, PATCH-037에서 실제 실행·회복을 포함한 고정 기준을 판정한다. 현 단계는 전체 챗봇 품질 승인이나 기본 기능 활성화를 의미하지 않는다.
