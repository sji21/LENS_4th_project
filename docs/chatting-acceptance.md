Python 1,392개 + subtest 137개, JavaScript 5개, Django system check가 통과했다. 선택적 LangSmith 2개·개인 PDF 1개는 미실행이다. 실제 모델은 같은 Qwen3-8B Q4와 KURE-v1, 동일한 175개 청크·저장 벡터를 사용했다. 각 원시 결과에 모델 digest, 임베딩 revision, 소스 해시, 전후 검색 자료 검증이 있다.

개발 평가 01의 DEV-006 / 2는 판단 제안 거절 후 다른 사람의 전세·종료·미반환 사실이 활성 상태에 남았다. 수정 경로는 과거 화면 이력을 유지하되 활성 사실과 문맥을 폐기한다. 새로운 사실을 추측해 채우지 않으므로 해당 턴의 필수 사실 점수는 떨어질 수 있다.

## 실제 화면과 법률 답변의 한계

별도 임시 DB·고정 응답으로 확인 질문 선택, 자유 입력, 쉬운 설명·요약, 오류 뒤 입력 보존, 두 문서 업로드·선택·삭제, 새 대화와 새로고침을 브라우저에서 확인했다. 수정 후 문서 버튼은 원래 질문을 전송하고 선택한 문서를 표시했다. 390×844 화면에서 버튼·입력창 겹침과 콘솔 오류가 없었다. 이 검사는 LLM/OCR의 정확도 평가가 아니다.

실제 Qwen 브라우저 상담에서는 상담 요청을 인사로 처리한 사례, 확인 질문 요청을 RAG로 보낸 사례, 일반 보증금 미반환에 초과 지급 보증금 조항을 제시한 사례가 있었다. 계약 미종료 답변 뒤 반환 의무를 바로 단정한 문장도 기존 검증을 통과했다. 검증 통과 표시만으로 상황에 적절한 법률 답변임을 보장할 수 없다. 기존 법률 검증 담당자와 재현 입력·출처·공개 답변을 함께 검토해야 한다. 법률 정책을 임의로 확장하거나 기준을 낮추지 않았다.

구조·실행·한계·기존 경로 복귀는 [팀 인계 문서](chatting-handoff.md)를 참고한다. 기본 기능 플래그는 false이며 main 병합·푸시·배포는 수행하지 않는다.

## 별도 수용평가의 수동 확인

개발 03과 수용평가 사이 소스 해시가 동일했고, 기준선·개발·수용평가의 모델 identity와 검색 청크·저장 벡터도 동일했다. 별도 수용평가 결과를 본 뒤 제품 코드나 프롬프트를 조정하지 않았다. 이후 이 사례를 보고 수정하면 재실행은 독립 평가가 아닌 회귀 검사로 표시해야 한다.

- ACC-001 / 2: 요약 요청의 잘못된 상담 대상 제안으로 판단이 거절되고 월세 문맥이 사라졌다.
- ACC-003: 반환을 기다린다는 진술을 미반환 사실로 저장하지 못했고, 만기 정정 뒤에도 필수 사실을 유지하지 못했다. / 2의 금지 문자열은 `만기가 지난 게 아니라`의 부정 문맥이므로 과거 만기를 긍정한 것으로 해석하지 않는다. 원시 실패 점수는 보존한다.
- ACC-004 / 1: 누수 상담에서 잘못된 사실 제안을 거절한 뒤 필요한 월세·수리 문맥도 비워졌다.
- ACC-005 / 2: `거기에`라는 첨부 문서 후속 질문이 판단 실패 뒤 일반 경로로 넘어가 거절됐다.
- ACC-006: 확답하기 어렵다는 표현에서 문맥 유지가 실패했다. 다음 턴에는 `계약갱신`이 상담 대상(subject)으로 저장되었다. 문자 인용 일치만으로 사실 필드의 의미까지 보장되지 않는 사례다. 금지된 과거 사실 검사 통과를 모든 사실이 올바르다는 뜻으로 해석하지 않는다.

개발 03과 수용평가에서는 새 확인 질문(clarify)이 생성되지 않았다. UI fixture에서 선택지가 동작한 결과를 실제 모델이 필요한 확인 질문을 잘 선택한다는 증거로 사용하지 않는다.

초기 평가 시점에는 37번의 코드·테스트·평가 자료를 `test/patch-037-chatting-acceptance` 작업 트리에 미커밋 상태로 보존했다. 이후 사용자 지정 대화 계층 범위의 보정과 검증은 `02a6434`에 커밋했으며 [후속 보고서](chatting-recovery.md)에 구분했다. 원시 결과의 commit 필드는 실행 시 부모 HEAD이며, 실제 평가 소스는 함께 기록된 파일별 SHA-256으로 식별한다. 기본 기능 플래그는 false를 유지한다.
