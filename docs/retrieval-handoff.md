## 2. 쓰는 법

```python
from src.retrieval.service import RetrievalService

service = RetrievalService.from_index()      # 앱 기동 시 1회
result = service.search("전세 사는 중에 집주인이 바뀌면 보증금은 어떻게 되나요?")

result.laws                  # list[Evidence] — 법령 5건
result.cases                 # list[Evidence] — 판례 5건
result.guides                # list[Evidence] — 공식 안내 0~2건 (질문 주제에 따라)
result.as_prompt_context()   # 프롬프트에 그대로 넣을 문자열
result.is_empty()            # 근거를 하나도 못 찾았을 때 ABSTAIN 판정용
```

건수 조절이 필요하면 `service.search(question, k_law=3, k_case=2)`.

생성 모델이 법령 상위 3건만 쓰므로 법령 Hybrid는 `rrf_k=5`를 사용합니다. 서비스
인덱스의 법령 채점 24문항에서 기존 60은 `dev-003`의 제3조와 `dev-008`의 제4조를
각각 4위에 두었고, 5로 낮추면 Hit@1 변화 없이 두 조문이 모두 3위가 됐습니다.
판례·안내의 `rrf_k=60`은 그대로이며 검색 후보 깊이(`depth=20`)도 바꾸지 않습니다.

복합 근거가 필요한 법령 질문은 Hit만으로 충분하지 않습니다. `dev-001`은 제3조가
2위였지만 제3조의2가 7위라 생성 모델의 상위 3건에 들어오지 않았습니다. 법령 BM25에만
확정일자의 부재·필요성·효력을 묻는 문맥을 `우선변제권·우선하여 변제`로 확장해
제3조의2를 3위로 올렸습니다. 부여 장소를 묻는 절차 질문에는 이 확장을 적용하지 않고,
판례·안내의 질의 확장기도 변경하지 않습니다. 법령 코퍼스에 존재하는 정답만 분모로
계산한 Recall@3는 97.9%에서 100%가 됐고 Hit@1 19/24·Hit@3 24/24는 같습니다.

이 규칙은 확인한 dev 24문항과 이미 공개된 holdout 18문항 중 `dev-001` 한 문항에서만
발동했습니다. 따라서 일반화 성능을 입증한 결과가 아니라 현재 상위 3건 계약의 누락을
막는 제한된 보강입니다. 확정일자 효과 질문과 신청·발급 절차 질문을 더 확보해 새
평가셋에서 재검증해야 합니다. 재현 명령은 `python -m src.evaluation.compare_law_top3`,
원자료는 `data/eval/runs/law-top3-comparison.json`입니다.

문맥 확장은 `"없이"` 같은 일반 낱말만으로 켜지지 않습니다. `확정일자 없이`처럼
부정 대상을 직접 확인한 뒤 신청·발급·서류·수수료 등의 절차 신호가 있으면 차단합니다.
우선변제·효력처럼 효과 의도가 명시된 질문은 절차 표현이 함께 있어도 효과 근거를
보강합니다.

### Evidence 필드

| 필드 | 내용 |
| --- | --- |
| `rank` | 그 묶음 안에서의 순위 (1부터) |
| `citation` | `주택임대차보호법 제3조(대항력 등)` / `대법원 2011다49523 추심금 (2013-01-17 선고)` |
| `text` | 조문·판시 본문 |
| `score` | RRF 점수. 절대값에 의미 없고 **같은 질문 안에서의 상대 순서**만 봅니다 |
| `source_url` | 국가법령정보센터 링크 |
| `chunk_id` / `doc_type` | 추적용 |

### 공식 안내는 별도 묶음입니다

HUG·국세청 안내를 `result.guides` 로 따로 돌려줍니다. **법적 근거가 아니라 실무 안내**라
조문과 같은 무게로 넘기면 모델이 "법에 따르면 보증 한도는…" 같은 문장을 씁니다.
프롬프트에서도 `## 참고 안내 (법적 근거가 아닌 기관 안내)` 로 표시됩니다.

원문을 그대로 수집했습니다 — HUG 2,807자, 국세청 595자를 6청크로 나눴습니다.
요약해서 넣지 않았습니다.

국세청 안내는 페이지 작성일 `2023-06-30`을 `effective_date`에 기록합니다. HUG 상품
안내는 페이지에 게시일이 없어 `effective_date`를 비워 두며, 수집일 `collected_at`과
`published_at_source=unknown`을 별도 메타데이터로 남깁니다. 수집일을 게시일이나
시행일로 취급하지 않습니다.

| 코퍼스 | 규모 |
| --- | --- |
| 법령·시행령 | 133청크 |
| 판례 | 26청크 |
| 공식 안내 | 6청크 |
| **Chroma 합계** | **165청크** |

법령 5칸을 안내가 먹지 않습니다. 기본 검색은 **법령 5 + 판례 5 + 안내 0~2 = 10~12건**
이고, 법령 목록에는 `law`·`decree`만 들어갑니다. 안내 건수는 질문 주제에 따라 달라지며
법령·판례 건수에는 영향을 주지 않습니다.

#### 안내 반환 기준 — 0~2건 가변

안내 검색은 모든 질문에 고정적으로 실행하지 않습니다. 질문이 현재 지원하는 안내
주제와 관련된 경우에만 검색하며, 관련성이 없으면 **0건**을 반환합니다. 단일 주제
질문에는 원칙적으로 가장 관련 있는 청크 **1건**을 반환하고, 하나의 청크만으로 답변
근거가 부족하거나 복수 안내 주제가 포함된 경우에만 **최대 2건**을 반환합니다.

현재 안내 자료와 평가 표본이 적어 전역 유사도 임계값은 쓰지 않습니다. 문서 2건·표본
5개로 문턱을 정하면 그 표본에 맞춘 값이 됩니다. 대신 주제별 의도 조건으로 검색 대상을
제한합니다.

| 질문에 포함된 의도 | 검색 대상 |
| --- | --- |
| 전세보증 · 반환보증 · HUG · 보증 가입/신청/보증료/한도 | HUG 안내 |
| 미납국세 · 세금 체납 · 임대인 세금 · 국세 열람 · 납세증명 | 국세청 안내 |
| 두 의도가 모두 있음 | 각 안내에서 1건씩, 최대 2건 |
| 어느 조건에도 해당하지 않음 | 0건 |

같은 안내문에서 두 번째 청크까지 넣는 것은 **그 청크가 질문의 낱말을 직접 담고 있을
때**뿐입니다. 검색 순위가 2위라는 이유만으로는 넣지 않습니다.

실제 동작입니다.

```
묵시적 갱신이면 계약 기간이 얼마가 되나요?          안내 0건
계약갱신요구권은 몇 번까지 쓸 수 있나요?            안내 0건
전세보증금반환보증은 어떤 제도인가요?               안내 1건  [보증보험]
보증 신청 절차만 따로 묻는 질문                       안내 1건  [보증보험]
집주인이 세금 안 낸 게 있는지 확인할 수 있나요?      안내 1건  [미납국세]
전세보증 가입하려는데 집주인 미납국세도 확인하고…    안내 2건  [보증보험 + 미납국세]
```

**법령·판례 반환 건수에는 영향을 주지 않습니다.** 안내는 별도 묶음이라 조문 5칸을
차지하지 않습니다.

안내 문서와 평가 질문이 늘어나면 유사도 임계값을 측정해 추가하면 됩니다. 그때까지는
재현 가능한 주제 조건으로 둡니다.

관련 여부 판정은 코드가 하지만, 그래도 무관한 안내가 섞일 수 있으므로
`as_prompt_context()` 가 다음 지시를 근거와 함께 실어 보냅니다. 별도로 프롬프트에
넣지 않아도 됩니다.

```text
## 참고 안내 (법적 근거가 아닌 기관 안내)
아래 자료는 질문과 관련될 때만 사용하세요. 관련이 없으면 무시하고 언급하지 마세요.
법령이 아니므로 "법에 따르면" 이라고 인용하지 말고 어느 기관의 안내인지 밝혀 주세요.
```

안내를 아예 끄려면 상한을 0 으로 둡니다.

```python
service.search(질문, k_guide=0)
```

## 5. 알고 있어야 할 것

### 법령과 판례를 섞지 않습니다

한 통에 넣고 뽑으면 서로를 밀어냅니다. 섞어서 측정했을 때 법령 Hit@5가 **17.4%p**
떨어졌습니다. 프롬프트에서도 `## 관련 법령` / `## 관련 판례`로 구분을 유지하세요.
판례는 그 사건의 사실관계 위에서 나온 판단이라 조문과 같은 무게로 읽으면 안 됩니다.
섞어 넘기면 모델이 판례 문장을 법조문처럼 인용합니다.

### 상가 법령은 기본으로 빠집니다

LENS는 주택 서비스인데 법령 133청크 중 57청크(43%)가 상가 법령입니다. 그대로 두면
주택 질문에서 상가 조문이 1위로 올라옵니다. 질문에 상가 신호(`상가`, `점포`, `가게`,
`사무실`, `권리금`, `환산보증금`)가 있을 때만 포함합니다.

| 평가셋 25문항 (전부 주택 질문) | Hit@1 | Hit@5 |
| --- | --- | --- |
| 라우팅 없음 | 40.0% | 92.0% |
| 라우팅 적용 | **76.0%** | 96.0% |

96%가 이 코퍼스의 **상한**입니다. 아래 "평가와 서비스가 보는 코퍼스가 다릅니다"를 보세요.

낱말 표에 없는 표현은 못 잡습니다. 사용자가 "제 가게 임대차..."가 아니라 다른 말로
쓰면 주택 범위로 처리됩니다.

### ⚠️ 판례 검색 성능은 수치로 주장하지 마세요

현재 판례 26건의 본문은 **평가 문항을 보고 작성된 요약문**입니다. 질문의 구어체
표현("집주인이 바뀐 경우", "아무 통지 없이 계약이 자동 연장되는")이 문서에 그대로
들어가 있어서, 검색이 잘 되는 것이 당연합니다. 발표에서 판례 검색 정확도를 숫자로
말하면 안 됩니다. **법령 검색 수치는 정상적으로 측정한 것이라 그대로 쓰셔도 됩니다.**

판례를 원문으로 교체하면 전부 다시 재야 합니다.

### 폐지 조문과 빈 질문

`status=current` 가 기본 필터에 들어 있어 폐지·구버전 조문은 반환되지 않습니다. 폐지된
조문을 근거로 답하면 사용자가 지금 없는 권리를 믿게 됩니다.

옛 조문을 일부러 찾아야 하는 화면이 생기면 이렇게 풉니다.

```python
from dataclasses import replace
from src.retrieval.service import LAW, RetrievalService

historical = replace(LAW, status="")          # status 조건만 뺀 사본
service = RetrievalService(chunks, dense, law=historical)
```

빈 질문(`""`, 공백, 탭·개행만)은 빈 결과를 돌려줍니다. `result.is_empty()` 로 확인하고
ABSTAIN 처리하면 됩니다. BM25 는 토큰이 없어 스스로 아무것도 내지 않지만, 임베딩은
공백도 벡터로 바꿔 아무 문서나 가장 가까운 것으로 돌려주기 때문입니다.

### 컨텍스트 크기

| 구성 | 길이 | 대략 토큰 |
| --- | --- | --- |
| 법령 5 + 판례 5 (`k_guide=0`) | 약 4,900자 | 2,400 |
| 안내 주제 질문 (법령 5 + 판례 5 + 안내 1~2) | 5,600~6,300자 | 2,800~3,100 |

안내는 관련 질문에만 붙고 1건당 약 700자입니다. 무관한 질문에서는 0건이라 늘지 않습니다.

청크는 규격상 `[법령명 제N조(제목)]` 헤더로 시작합니다(165건 전부). `as_prompt_block()`
이 그 경우 출처를 다시 붙이지 않으므로 프롬프트에 같은 문장이 두 번 들어가지 않습니다.

## 6. 검색 쪽에 남은 일

검색 후속 작업은 이미 끝낸 기반과 실제로 남은 검증 조건을 구분합니다. 생성·앱 작업이나
현재 제출 버전을 막지는 않습니다.

### 데이터가 갖춰지면 하는 일

1. **검증된 판례 코퍼스 확대·재평가** — 수집·파싱·검증·적재 파이프라인은 구현했고,
   최종 검색 평가는 검토·재현 가능한 26건을 기준으로 끝냈습니다. 추가 판례는 출처,
   사건정보, 판결요지와 주택임대차 도메인 적합성을 확인한 뒤 반영하고 모든 수치를
   다시 잽니다. 과거 207건은 검토 전 스테이징 기준선이지 적재·검증 완료 건수가 아닙니다.

2. **가이드 문서 확대와 라우팅 정량 평가** — 현재는 공식 문서 2건·6청크뿐입니다.
   서로 다른 사용자 의도를 다루는 공식 안내를 추가하고, 관련·무관 질문이 충분히
   모이면 현재 주제 조건과 유사도 문턱을 비교합니다. 지금은 0~2건 조건부 반환과
   법령·판례로부터의 격리만 기능·회귀 테스트로 확인했으며 별도 정확도를 주장하지 않습니다.

3. **코퍼스 변경 후 전체 재측정** — 법령·판례·안내가 늘거나 본문이 바뀌면 기존 결과를
   그대로 적용하지 않습니다. 상가건물임대차보호법 하나를 추가했을 때 MRR이
   0.581 → 0.446으로 떨어진 적이 있습니다.

### 평가 자체를 손봐야 하는 일

4. **법령 Holdout-v2 평가셋** — 기존 법령 Holdout 18문항의 1회 측정과 공개 후 회귀
   확인은 끝났습니다. 다음 검색 설정 변경 전에는 새 질문과 정답을 결과 확인 전에 봉인해
   측정합니다. 기존 결과는 TOP3 17/18(94.4%)입니다. 판례는 26건 코퍼스 기준 외부
   8문항 대체 Holdout까지 측정했지만, 표본이 작아 일반화 성능을 확정하지 않습니다.
5. **상가 질문 순위 평가** — 상가 신호에 따른 라우팅 기능 테스트는 완료했지만 정답
   라벨을 둔 순위 평가는 하지 않았습니다. 주택 서비스 제출 범위 밖이므로 낮은 우선순위입니다.

### 구현·재검증으로 남은 일

6. **법령·판례별 BM25 `b` 재측정** — 법령 `b=0.25`, 판례 `b=0.75` 초기 실험은
   끝났지만 현재 서비스는 둘 다 기본 `b=0.75`를 사용합니다. 검증된 판례 코퍼스와
   법령 Holdout-v2가 준비된 뒤 다시 측정해 운영값 채택 여부를 판단합니다.
7. **`fetch_law_mock` 덮어쓰기 수정** — 지금은 실행할 때마다
   `data/sample/chunks_expanded.jsonl` 을 법령 133건으로 덮어써 가이드 2건을 지웁니다.
   위 3절의 경고와 복구 절차가 그것 때문입니다. 법령이 아닌 청크는 보존하도록 고쳐야
   하지만 현재 제출 차단 사유는 아닙니다.
8. **TOP3·TOP2 리랭커 비교** — BM25+KURE+RRF와 생성 입력 건수는 확정했지만 별도
   리랭커는 구현하지 않았습니다. 검색 지표뿐 아니라 생성 정확도와 지연시간을 함께
   비교해야 합니다.
9. **민법 조건부 라우팅 재도입 검토** — PATCH-033에서 구현하고 Dev·기존 Holdout 회귀,
   자연어 발동·오발동을 확인했지만 최종 제출에서는 제외했습니다. 독립 평가와 운영
   코퍼스 재적재 조건이 갖춰질 때 적용 여부를 다시 판단합니다.
