# PATCH-021 — 일반 법령과 민법 후보 반환 분리

## 변경

PATCH-020의 잠정 TOP3 결정을 실제 검색·생성 연결에 반영했다. `RetrievalResult.laws`에는 일반 법령만, 새 `civil_laws`에는 민법 후보만 담는다. 기존처럼 민법이 일반 법령의 반환 개수를 차감하지 않는다. DB·청크·인덱스·임베딩 모델은 변경하지 않았다.

| 필드 | 검색 API 기본값 | Qwen 경로의 기본 요청 |
|---|---|---|
| laws | 일반 법령 최대5 | 기존 최대3 유지 |
| cases | 판례 최대5 | 기존 최대2 및 단계형 추가 조건 유지 |
| civil_laws | 민법 후보 최대3 | 별도 최대3 |
| guides | 기관 안내0~2 | 기존0~2 유지 |

민법은 기존 규칙의 최대2개 선택을 보존한 뒤, 민법7개 RRF 검색 후보에서 중복 없이 최대3개까지 채운다. 각 목록의 `rank`는1부터 시작하며, 서로 다른 목록의 통합 관련성 순위가 아니다. `civil_topics`는 기존 규칙으로 감지된 주제를 유지하며 보충 후보의 적용 판단을 의미하지 않는다.

`search(..., k_civil=0)`으로 민법만 끌 수 있다. `k_civil`은 키워드 전용이며 최대3으로 제한한다. 생략 시 기존 `k_law=0` 호출은 민법도 끄므로 판례만 추가 검색하거나 문서만 질문하는 경로를 보존한다. 명시적으로 `k_law=0, k_civil=3`이면 민법만 검색할 수 있다. 빈 질문·보유 자료 없음은 민법0개다. **관련 없는 질문을 자동 판별해 민법0개를 선택하는 조건은 아직 없다.**

## 호출부 호환과 생성 연결

- 기존 위치 인자 순서를 유지하고 새 dataclass 필드는 마지막에 추가했다.
- 법령을 전부 사용하려던 외부 호출부는 `laws`만 읽지 말고 `civil_laws`도 확인해야 한다. 전체 출처에는 `RetrievalResult.evidences`를 사용할 수 있다.
- `Answer.civil_laws`, `Answer.evidences`, `sources()`에 민법을 연결했다. 민법의 `doc_type`은 계속 `law`다.
- 단계형 검색이 결과를 복사할 때 민법 후보·감지 주제를 보존한다. 프롬프트 본문과 출처명에 별도 `관련 민법 후보` 구간을 제공한다.
- chain과 graph 모두 민법을 조건 교정·인용 검증·답변 결과에 전달한다. 답변 실패·검증 보류 경로에서도 반환된 민법 출처가 사라지지 않는다.
- 기존 법령 TOP3·판례 TOP2 요청 설정, 생성 모델, 안전성·답변 판단 규칙은 변경하지 않았다. PATCH-019의 보안·환경 작업과 별개로 필요한 연결 필드만 추가했다.

## 검증

1. 실제 변경된 `RetrievalService.search(k_law=5,k_case=5,k_guide=2)`로 DEV200+CIV35의235입력을 복사 인덱스에서 실행했다.
2. 모든 입력의 일반 법령 순위와 민법 후보가 PATCH-020의 `general` 및 `retain_3`와 정확히 일치했다.
3. 판례·안내의 청크 순위는 PATCH-015와235입력 모두 같았다. 운영 DB·청크·인덱스 파일 전후 해시도 모두 같았다.
4. 전체 테스트 **756 passed, 3 skipped, 124 subtests passed**. 처음에는 로컬 Django 미설치로 수집이 중단됐고 requirements에 이미 명시된 Django5.2.17·pytest-django4.14.0을 가상환경에 설치한 뒤 전체 통과했다. 건너뜀은 추적 비활성 LangSmith2건과 비공개 PDF 미지정1건이다.
5. 단계형 검색·프롬프트·chain/graph 답변·출처 연결을 가짜 LLM으로 검증했다. 실제 Qwen의 법적 판단 정확도나 응답 품질은 평가하지 않았다.

민법 부분 확보율은 기존 실험과 같은 CIV29/29, DEV 질문 단독10/10·문맥9/10이다. **DEV-059 문맥의 제626조 누락은 남는다.** 신규 CIV 전체 필수 법령28/29와 민법 부분29/29는 구분한다. 공개 개발용 조문 단위 회귀이며 독립 평가가 아니다.

실제 검색 재검증에는 PATCH-015와 같은 운영 자료·모델 캐시가 필요하다. 실행기는 원래 자료를 임시 경로로 복사하고 모델을 오프라인으로 읽는다. 운영 원본을 수정하지 않으며 새 출력 경로만 허용한다. 실행 당시 코드와 미커밋 상태는 감사 기록에 보존했다.

이전 PATCH-015~020 재현기는 당시 제품 코드 해시를 고정 검증하므로 이번 제품 변경 후에는 실행을 거부할 수 있다. 이전 결과 재현은 해당 커밋의 별도 체크아웃에서 수행하고 현재 검색 검증은 PATCH-021 실행기를 사용한다.


## PR #19 평가기 정정

일반 법령만 읽던 평가기는 분리된 민법 정답을 검색 실패로 기록할 수 있었다. 평가 범위를 명시적으로 구분했다.

- 기본 `--law-scope general`: 일반 법령 TOP5의 Hit/Recall@1·2·3·5 및 MRR.
- `--law-scope civil`: 별도 민법 TOP3의 Hit/Recall@1·2·3 및 MRR. TOP5 지표는 만들지 않는다.
- `--law-scope combined`: 일반5+민법3의 합집합에 대한 Hit·전체 필수 근거 충족·Recall. 두 채널 사이의 통합 순위나 MRR는 정의하지 않는다.
- 일반/민법 단독 범위와 정답 종류가 다르면 실행을 거부하고 범위 선택을 요구한다. 판례 평가는 유지한다.

`evaluate_civil_regression`의 공개 세트는 일반 법령8문항과 민법7문항을 포함하므로 전체15문항을 combined로 채점한다. 비정답5문항은 기존 제외를 유지하고 실제 민법 노출 청크도 기록한다. 기존 보고서의 혼합 TOP5/MRR와 새 합집합 점수는 직접 비교하지 않는다.

검증: 실제 공개 세트의 정답을 각 채널로 반환하는 모의 서비스에서15문항 전체가 정상 채점됨을 확인했다. 이는 평가기 검증이며 실제 검색 성능100%를 뜻하지 않는다. 전체 테스트768 passed, 3 skipped, 124 subtests passed. 이번 정정에서는 새 벡터 검색을 실행하지 않았고 기존235입력 결과·정답·코퍼스는 수정하지 않았다.


## PR #19 커밋 기준 재검증

검증기 정정 커밋 `373c465`의 깨끗한 작업 트리에서235입력을 다시 실행했다. 새 audit의 `source_provenance`는 실행 커밋·Git 트리·실행기 및 검색 코드의 작업 파일/Git 원본/LF 정규화 SHA-256을 기록한다. 실행 전후 같은 출처인지 확인하며 미커밋 변경은 거부한다.

235입력의 결과 파일은 이전 기록과 바이트 단위로 동일하고 운영 자료의 전후 해시도 같다. 전체 테스트는771 passed, 3 skipped, 124 subtests passed다. 현재 `audit.json`은 이 재검증 기록이며 원래 커밋 전 기록과 그 manifest·결과는 `initial-capture/`에 보존한다. 최초 `service_sha256` 차이는 혼합 개행 때문이며 LF 정규화 후 Git 코드와 일치했다. 원래 기록의 해시나 실행 커밋을 소급 변경하지 않았다.
