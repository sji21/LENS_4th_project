# PATCH-042 DEV 검색 누락·기존 근거 손실 분석

이 문서는 개선 전 기준선과 분석 결과를 보존한다. 이후 사용자 승인으로 진행한 구현·개선 검증은 [검색 개선 기록](patch046-retrieval-improvement.md)에서 구분한다.

## 결론

개선 여지는 있다. 다만 이번 분석에서 운영에 바로 적용할 만큼 개선·회귀가 검증된 정책은 없다. 우선 검토할 대상은 **질문의 핵심 의도와 필요한 이전 사실 보존, 후보 순위 결합, 서로 다른 종류의 필수 근거 동시 확보**다.

현재 질문·문맥 각각 32입력이 불완전하며, 중복 제거하면 37문항이다. 누락된 필수 조문은 83개의 `(문항, 모드, 조문)` 조합이고 고유 조문은 25개다. 이 조문은 모두 DB에 있다. 근거 수 자체가 일반5·민법3의 반환 한도를 넘는 문항도 없다. 데이터 추가나 반환 개수 증가를 먼저 정답으로 정하지 않는다.

## 기준과 실행

- 기준 코드: PR29 병합 main `9c816c3`. 분석 브랜치 `feat/patch-042-retrieval-gap-analysis`.
- 고정 입력·정답: 기존 DEV100 v2 질문100·문맥100 및 민법35. DEV의 필수 채점 대상은 모드별75이며 무목표23·과거판본 검토2는 별도다.
- 기준 결과: PATCH-041 최종 capture. 일반 법령5·민법3·판례5·안내 최대2를 구분한다.
- 실제 현재 검색기를 같은235입력으로 실행하고 BM25·KURE 구성원 순위, 전체 후보 결합 순위, 민법 seed·준용 쌍 선택을 관측했다. 실제 검색의 질의·후보 깊이·가중치·선택·반환 수를 바꾸지 않았다.
- 로컬 CPU, 기존 PATCH-041 별도 작업 폴더의 재구축 데이터를 사용했다. KURE 실제 호출375회, 일반 backend494회·민법298회. **235입력 전체의 네 채널 반환 근거·순위와 채점 지표가 PATCH-041과 일치했다.** 기존 capture는 검색 원점수를 저장하지 않으므로 원점수 일치까지 주장하지 않는다.
- 인덱스 로딩 과정에서 Chroma 파일6개의 바이트가 변경됐다. 이를 감사 기록의 `index_opening_changes`에 보존했다. 로딩 후 검색 전후 파일 해시, 인덱스 내용·메타데이터·벡터의 논리 해시와 모델·제품 소스 해시는 동일하다. 원천·조문 추가나 인덱스 재구축을 수행한 것은 아니다.
- 과거 `verified_context`의 문맥42/75·반환손실8건을 현재 값으로 재사용하지 않는다. 최종 `record_lookup`에서 DEV-099 문맥의 확정일자 기록 근거가5위로 회복돼 문맥43/75·반환손실7건이 됐다.

민법은 후보 깊이26과 코퍼스26조문이 같아 모든 조문이 후보에 나타날 수 있다. 따라서 ‘민법 후보에 있었다’를 좋은 의미 검색 성적으로 해석하지 않는다.

과거143조문 운영 결과에서 반환했던 필수 근거가 현재 빠진 목록이다. PATCH-041 재구축이나 이번 분석이 새로 만든 손실이 아니다. 표는 잃은 목표만 보여주며 해당 질문의 다른 누락은 상세 자료에 포함한다.

| 입력 | 잃은 목표 | 현재 관측 |

## 4. 저장 순위로만 비교한 두 가지 대안

실측 후보를 재조합한 진단이다. 새 정책으로 실제 검색한 결과나 운영 개선 성적으로 보고하지 않는다. 질문·정답을 이미 본 개발 분석이며 새 Holdout 성적도 아니다.

| 대안 | DEV 질문 완전 확보 | DEV 문맥 완전 확보 | 민법35 필수 완전 확보 |

| 현재 일반5+민법3 | 43/75 | 43/75 | 28/29 |

### 일반 TOP10

현재5개를 그대로 포함하므로 기존 목표 손실0은 구조적으로 당연하다.23입력에서 추가 목표를 확보하지만, 문맥에서는 완전 확보가2입력만 늘어난다. 반환 근거가 늘며 생성에 전달하면 프롬프트 길이·무관 근거 노출·지연·비용이 늘 수 있지만 실제로 측정하지 않았다. 검색 구성원의 후보 깊이는20으로 동일하다. 현재보다 좋은 정책이라고 채택하지 않고, **6~10위 후보를 현재 예산 안에서 잘 선택할 여지가 있는지** 검토하는 용도로 사용한다.

### 민법 세 번째 후보 교체 생략

- 회복: DEV-059 질문의 민법 제626조.
- 추가 확보: DEV-064 문맥의 민법 제105조.
- 새 손실: DEV-058 문맥의 민법 제627조.

과거 분석에서 지적한 상충 관계가 현재 최종 검색에서도 재현된다. 한 건의 순이득만 보고 이 규칙을 삭제하지 않는다.

## 5. 검색 반환과 생성에 전달하는 근거 수

현재 `src/generation/chain.py`의 기본 일반 법령 요청 수는3이다. 실제 호출이 이를 덮어쓸 수 있으므로 모든 배포 요청이3개라고 단정하지 않는다.

현재 순위의 일반3+민법3만 보면 DEV 완전 확보는 질문40/75·문맥38/75다. 일반5에서는 완전하지만3에서는 불완전한 입력이 질문3·문맥5개 있다. 이는 과거 대비 ‘TOP3에서만 추가 손실3입력’과 다른 집계다.

또한 DEV-003·025는 일반 필수 조문5개, DEV-026·028·038은4개다. 이5문항은 각 모드에서 일반3개만 전달하면 순위를 완벽히 고쳐도 고정 필수 근거를 모두 전달할 수 없다. 일반5 반환의 용량초과0과 일반3 소비의 구조적 제약을 혼동하지 않는다. 생성 담당과 근거 예산을 별도로 논의할 사항이다.

검색기에서 확보한 근거가 생성에 전달되는 범위와 실제 답변 품질은 별도로 확인해야 한다. 이번 분석은 LLM을 호출하지 않았고 생성 설정도 변경하지 않았다.

## 6. 다음 실험 우선순위와 반례

1. **현재 요청과 필요한 사실을 보존하는 검색 입력·순위 검토.** 대리 권한(DEV-001·012·013), 혼합 주거/영업 적용 범위(DEV-009), 국세/지방세 조회(DEV-003·025~028)를 묶는다. 한쪽 검색기에서 이미 높은 근거가 밀리는 경우를 먼저 추적한다. 문맥으로 회복하는 사례와 악화하는 사례를 모두 검증한다.
2. **서로 다른 절차·근거 종류의 동시 확보.** 전입·확정일자·임대차 신고, 국세·지방세 및 시행령, 합의·대리·등기처럼 질문이 요구하는 여러 역할을 구분한다. 특정 문항 ID나 조문 번호를 강제로 올리지 않고, 실제 질문에 드러난 의도에만 반응하는 후보를 검토한다.
3. **후보 TOP20에도 없는9조합의 입력·개념 표현 검토.** 전체 후보 깊이를 먼저 늘리기보다 현재 요청을 반영한 질의인지, 기존 확장어가 다른 주제를 앞세우는지 확인한다. 사기 신고와 민사 반환, 전입과 계약 신고 등을 구별하는 비관련 반례도 포함한다.
4. **민법 마지막 슬롯은 보류.** DEV-059·064 회복과 DEV-058 보존을 함께 만족하는 일반적인 근거 선택 방식이 검증되기 전에는 기존 정책을 유지한다.

튜닝 전에는 새 Holdout-v2의 질문·정답을 별도 담당자가 봉인하고, DEV와 기존 공개 회귀는 개선·회귀 분석용으로 구분하는 것이 필요하다. 동일 반환 예산 비교, 완전 확보·Hit@1/3/5·기존 목표 손실, 실제 생성 소비 범위와 실행 비용을 사전에 정한 기준으로 확인한다. 새 독립 질문을 이번 실패 목록에서 그대로 변형해 만들었다고 독립성까지 확보되는 것은 아니다.
