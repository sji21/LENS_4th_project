# 대화형 챗봇 인계

## 적용 범위와 실행

`chatting-upgrade`는 26~36번 구현을 통합하는 로컬 브랜치다. 최종 수용평가는 별도 37번 브랜치에서 완료했으나 기준에 미달했다. 사용자 요청으로 법률 적용·검증과 분리한 대화 계층 보정과 35턴 공개 회귀 검증을 37번에서 완료했다. 기존 평가 실패 기록은 보존하며 새 검증 결과는 [대화 복구 보고서](chatting-recovery.md)에 구분한다. 회원가입과 법률 검증 담당자의 정책 변경은 이 작업의 별도 영역이다.

```bash
python manage.py migrate
CHAT_CONVERSATION_ENABLED=true python manage.py runserver 127.0.0.1:8000 --noreload
```

Windows PowerShell에서는 `$env:CHAT_CONVERSATION_ENABLED="true"`를 설정한 뒤 같은 runserver 명령을 실행한다. `.env`를 사용해도 된다. 환경변수는 서버 시작 시 읽으므로 변경 뒤 서버를 다시 시작한다. 기본값은 `false`이며 기존 웹 경로가 유지된다. API 키나 실제 문서를 공유 저장소에 올리지 않는다.

## 사용자 입력에서 출력까지

1. Django가 세션 소유권·CSRF·요청 ID·동시 요청 잠금을 확인하고 입력을 마스킹한다.
2. 원래 입력의 공격·범위 검사를 먼저 수행한다. 문서와 대화 문맥으로 바꾸기 전에 검사한다.
3. 명확한 선택 답은 코드로 처리한다. 나머지는 같은 Qwen 모델에 현재 사용자 발언, 출처가 있는 사용자 사실, 제한된 이력과 소유 문서 목록을 전달하여 구조화된 의도·행동·사실 후보를 받는다.
4. 서버가 후보의 키, 값, 인용 출처, 부정, 숫자와 문서 소유권을 검사한다. 정정은 새 진술로 대체하고 다른 상담으로 전환하면 기존 사실을 비운다.
5. 인사와 확인 질문은 고정 안내로 표시한다. 법률 질문은 확인된 사용자 진술과 현재 질문으로 검색 질문을 구성하고 기존 RAG로 보낸다.
6. 생성 표현을 standard/simple/brief 중 하나로 요청한다. 법률 본문은 기존 근거·출처·조건·의미 검증을 통과한 뒤에만 반환한다. 검증 이후 재작성 호출은 없다.
7. 완성된 대화 상태와 공개 응답만 한 번 저장한다. 웹은 선택지, 보류 사유, 출처, 최근 확인 문서와 처리 상태를 표시한다.

이 구조는 여러 자율 에이전트가 협의하는 시스템이 아니다. 같은 LLM을 판단·생성·기존 의미 검증에 나누어 사용하고, 상태 변경과 실행 권한은 코드가 관리한다. 모든 문장을 시나리오로 하드코딩하지 않지만 모델의 판단 오류가 사라지는 것도 아니다.

## 파일과 연결 지점

| 파일 | 책임 |
| --- | --- |
| `chat/dialogue_state.py` | 사용자 진술·출처·정정·주제·pending·공개 답변 기억 |
| `chat/dialogue_contract.py`, `dialogue_planner.py` | 판단 입력과 엄격한 출력 계약, Qwen 한 번 호출 |
| `chat/dialogue_router.py` | 행동 분기, 확인 질문 복구, 원자적 상태 반영 |
| `chat/dialogue_recovery.py` | 판단 거절 시 맥락 보존·사건 구분 확인·선택 후 재개 |
| `chat/dialogue_clarification.py` | 고정 질문·선택지·반복 횟수 제한 |
| `chat/dialogue_documents.py`, `dialogue_query.py` | 소유 문서 선택과 사실 기반 검색 질문 |
| `src/generation/graph.py`, `prompt.py` | 기존 법률 검증 연결과 표현 스타일 |
| `src/generation/call_budget.py` | 요청별 모델 시도·시간 예산 |
| `chat/views.py`, `static/chat/` | 기존 API·CSRF·잠금과 화면 입력·상태 표시 |

외부 API에는 기존 `messages`, `documents`, `conversation_id`를 유지하고 `conversation`의 공개 선택 상태만 추가했다. 사용자가 확인 버튼을 누르면 `reply_to`에 질문 메시지 ID를 전달한다. 회원 담당자는 기존 `accounts.User`와 Django 세션을 사용하되 로그인 시 게스트 상담을 자동 승계할지 새로 만들지 정책을 먼저 정해야 한다.

## 검사와 복귀

```bash
python -m pytest -q
node --test tests/chatting_request_identity.test.cjs
node --check static/chat/app.js
python manage.py check
python -m src.evaluation.chatting_run --mode upgrade --split dev --output data/eval/chatting/results/new-dev.json
```

실제 평가에는 같은 Ollama 모델 digest, KURE revision, 전체 175개 검색 청크와 저장 벡터 검증이 필요하다. 수용평가 파일은 개발 중 튜닝에 사용하지 않는다. 원시 결과의 `complete`는 실행·출처 일관성일 뿐 품질 통과 여부가 아니다. [기준선과 고정 기준](chatting-baseline.md), [판단 모델 실험](chatting-planner.md), [화면 검증](chatting-web.md), [실패 복구](chatting-reliability.md)를 함께 확인한다.

롤백은 `CHAT_CONVERSATION_ENABLED=false` 후 서버 재시작이다. 데이터베이스 구조를 바꾸거나 커밋을 되돌릴 필요가 없다. 모드를 바꾼 뒤에는 새 대화를 시작해 이전 실험 이력과 섞이지 않게 확인한다. 이는 법률 검증의 품질 문제를 해결하는 조치가 아니라 기존 실행 경로로 복귀하는 방법이다.

## 브라우저 검증 재현

`python -m tests.browser_chatting_fixture`는 loopback 8800 포트, 별도 임시 DB와 쿠키 이름을 사용한다. 종료 시 임시 DB를 제거한다. 실제 LLM·OCR 호출을 고정 fixture로 대체하므로 이 결과를 답변 정확도 또는 OCR 품질로 사용하지 않는다.

확인 문구 `확인 질문 테스트` → `모르겠어요` 선택 → 쉽게 설명/요약 전송 → `오류 확인` 입력 보존을 확인한다. 두 업로드 전송 fixture를 올려 문서 선택, 최근 문서 표시, 새로고침, 문서 삭제와 새 대화를 확인한다. 이 작업에서 해당 흐름을 실제 브라우저로 검증했고 JavaScript 콘솔 오류는 없었다. 실제 모델의 대화·답변 품질은 별도 평가 결과로 판단한다.

## 최종 평가 중 발견한 회귀

개발 평가에서 문서 선택 원문 유지와 답변 질문 캐시를 보완했다. 이후 사용자 요청으로 실패 대화를 회귀 자료로 활용하여 다음 동작으로 변경했다.

- 부가적인 상담 대상·역할·건물 종류의 잘못된 제안은 제외하고 전체 판단 계약을 다시 검사한다. 금액·날짜·참/거짓 조건의 오류는 묵인하지 않는다.
- 판단 거절 시 기존 사실을 지우거나 기존 RAG로 즉시 보내지 않는다. 상담 정보를 보존하고 이전 상담/새 상담 선택과 질문 재진술을 요청한다. 새 상담 버튼은 모델 호출 전에 이전 사건을 초기화한다.
- 모델 연결 실패는 503으로 반환하며 상태를 변경하지 않는다. UI의 기존 재시도 및 요청 ID 보호를 사용한다.
- 후속 질문과 재설명은 직전 검증 답변의 질문 대상을 재사용한다. 사실·주제·문서 전환 시 캐시를 무효화한다.

새 회귀 범위와 실제 모델 평가는 [대화 복구 보고서](chatting-recovery.md)에 기록한다. 아래 검사 수치는 첫 수용평가 당시의 기록이다.

최종 자동 검사: Python 1,392개와 subtest 137개, JavaScript 요청 ID 검사 5개가 통과했다. 선택적 LangSmith 2개와 개인 PDF 1개는 기존 조건으로 미실행이다. 고정 기준 판정은 `python scripts/report_chatting_run.py <원시 결과 JSON>`으로 재현하며, 판단을 관측하지 못한 턴도 의도 평가의 필수 분모에서 빼지 않는다. 수치 통과만으로 법률 정확도·배포 승인을 선언하지 않는다.

2026-09-14 브라우저 재검증: 두 합성 문서에서 보증금·시작일을 묻고 B 문서 버튼을 누른 뒤 원래 질문이 그대로 전송되고 활성 문서가 B로 표시되는 것을 확인했다. 390×844에서 확인 질문·세 선택지·입력창이 겹치지 않았으며 콘솔 오류가 없었다. 첨부 문서와 확인 패널이 함께 있으면 대화 표시 영역은 좁아지므로 작은 화면의 긴 상담 사용성은 추가 개선 여지가 있다. 검증 서버와 임시 탭은 종료했다.

## 대화 계층 완료 후 인계 항목

- 보정한 공개 회귀 35턴은 대화 항목 기준을 충족했다. 의도 분류 1건의 오차와 새 미공개 대화의 독립 검증은 대화 복구 보고서에 남겼다.
- 초기 전체 RAG 응답 지연은 별도 후속 과제다. 이번 대화 계층 p95를 전체 답변 시간으로 표시하지 않는다.
- 법률 적용·검증 담당자는 실제 공개 답변의 상황 적합성을 확인한다. 기존 호출 인터페이스와 검증 구현은 유지했다.
