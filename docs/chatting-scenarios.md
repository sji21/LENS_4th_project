# 대화형 챗봇 평가 사례

이 문서는 4차 PATCH-048의 평가 데이터 계약이다. 제품의 대화 처리 규칙이나 법률 정답표가 아니다.
LLM은 입력과 대화 상태를 읽고 다음 행동을 판단한다. 개발자가 사례의 문장을 조건문으로 등록하거나
사례별 답변을 제품 코드에 넣어서는 안 된다.

## 데이터 구성과 사용 순서

| 파일 | 용도 | 사례 수 | 사용자 턴 수 |
| --- | --- | --- | --- |
| [dev.json](../data/eval/chatting/dev.json) | 개발·프롬프트 조정·기준선 비교 | 12 | 23 |
| [acceptance.json](../data/eval/chatting/acceptance.json) | 개발 조정에 사용하지 않는 최종 수용평가 | 6 | 12 |

각 사례는 독립된 대화이며 앞선 사례의 상태·문서·응답을 재사용하지 않는다. 개발용은 인사, 혼합 의도,
단답 연결, 정정, 부정, 상담 대상 전환, 쉬운 설명, 문서 후속 질문, 모름, 보류 후 추가 설명,
짧은 후속 질문, 검증 우회 요구를 포함한다. 수용평가에는 같은 능력을 다른 표현으로 확인하는 사례를 둔다.
위 개수는 실행 성공 건수가 아니라 고정된 평가 입력의 개수다.

1. 구현 전에 두 파일의 해시와 기준 코드·모델·설정을 기록한다.
2. 현재 처리 방식과 새 처리 방식에 같은 사용자 입력·가상 문서·사전 상태를 제공한다.
3. 개발 중에는 `dev`만 실행·열람해 프롬프트와 로직을 조정한다. 수용평가 본문을 프롬프트 예제로 넣지 않는다.
4. 최종 수용평가는 구현·프롬프트 설정을 고정한 후 별도 실행한다. 결과를 보고 수정했다면 해당 데이터는
   다음 평가에서 개발 자료가 되며, 같은 데이터의 재실행을 새로운 독립 성능으로 보고하지 않는다.
5. 수용평가 원문은 저장소에서 접근 가능하므로 비밀 봉인된 외부 평가라고 표현하지 않는다. 읽은 사람과
   사용 시점을 기록하는 운영 분리이며, 이미 열람했다면 그 사실을 결과에 적는다.

## JSON 계약

최상위에는 `schema_version: 1`, `split`, `cases`가 있다. 사례에는 고유 `id`, `category`,
`initial_state`, `documents`, 순서가 있는 `turns`를 둔다. 턴의 `user`는 모델에 실제로 제공할 사용자
메시지이고 `expect`는 평가자에게만 전달한다. 정답 라벨이나 허용 행동 목록을 모델 입력에 넣지 않는다.

`initial_state`가 빈 객체인 사례는 새 상담에서 시작한다. 단답 의미를 정확히 통제해야 하는 사례는
`pending_question`과 `pending_field`를 사전 상태로 명시한다. 모델이 먼저 어떤 질문을 했는지
확인하지 않고 무조건 다음에 “네”를 보내는 평가를 피하기 위한 것이다. 실행기는 사전 질문과 기존
사용자 진술을 양쪽 처리 방식의 문맥에 같은 의미로 전달한다. `last_answer_status: abstained`는
앞선 답변이 보류된 조건이며, 검증에 실패한 법률 본문을 사실로 삽입하는 조건이 아니다.

| 기대 항목 | 평가 의미 |
| --- | --- |
| `actions` | 허용되는 실행 행동. 여러 값이면 어느 하나를 충족하면 된다. |
| `intent` | 이번 입력이 대화에서 수행한 역할. 표현이 아니라 아래 역할 정의로 채점한다. |
| `facts` | 턴 처리 후 활성 상담 상태에 반드시 유지되어야 할 사용자 진술. 전체 상태의 완전 일치를 요구하지 않는다. |
| `forbidden_facts` | 활성 상담에 남아서는 안 되는 키·값 조합. 정정 전 정보와 다른 상담의 정보 혼입을 검사한다. |
| `query_contains` | RAG로 진행할 때 검색 질문에 보존되어야 할 최소 표현. 모든 필수 항목을 확인한다. |
| `query_excludes` | RAG로 진행할 때 검색 질문에 들어가면 의미가 달라지는 표현. |

`query_contains`와 `query_excludes`는 실제 RAG 행동을 수행한 턴에만 적용한다. 추가 질문이나 정정
확인으로 끝난 턴에서 아직 만들지 않은 검색 질문을 실패로 채점하지 않는다. 단순 문자열 포함은 의미
보존을 검사하는 보조 지표다. 동의어를 올바르게 썼거나 부정·인용 문맥 때문에 문자열 판정이 맞지 않으면
원래 자동 결과를 보존하고 별도 수동 판정 및 근거를 남긴다. 결과를 올리기 위해 사후에 라벨을 바꾸지 않는다.

`facts`의 계약 종류·종료 여부·거주 여부는 법적 사실의 확정이 아니라 사용자 설명을 기록한 값이다.
종료 여부를 모르는 입력은 `예`와 `아니요` 어느 쪽으로도 확정하지 않는지 수동·상태 테스트로 함께 확인한다.
정정 이력 보존은 허용하지만 오래된 값이 활성 상담이나 새 검색 질문에 사용되면 실패다.
문서에서 읽은 금액과 조건은 사용자 진술과 별도 출처로 저장해야 하므로 문서 사례의 `facts`는 비워 둔다.

## 의도·행동의 역할 정의

의도는 `greeting`(인사·서비스 안내), `question`(새 상담 질문), `followup`(기존 상담에 의존한 요청),
`correction`(이미 제공한 정보 정정), `clarification_answer`(대기 중인 특정 질문의 답),
`explain`(직전 설명을 쉽게 또는 짧게 표현), `topic_change`(다른 상담 대상·주제로 명시적 전환),
`document_question`(첨부 문서 내용의 확인·설명)으로 구분한다. 혼합된 인사와 상담은 실제 상담 요청을
우선한다. 모름도 대기 중인 질문에 대한 답이면 `clarification_answer`다. `explain`은 새 상황을
추가하는 요청과 구분하며, 첨부 문서의 다른 조항을 설명해 달라는 요청은 `document_question`이다.

기존 상담에 정보를 더하고 그 상황을 계속 물으면 `followup`으로 라벨링한다. 대기 질문에 대한 응답과
명시적 정정이 섞이면 정정 역할을 우선한다. 이 정의는 평가의 일관성을 위한 것이며 제품의 유연한 이해를
표현별 조건문으로 제한하지 않는다. 합리적인 의도 대안이 발견되면 실행 로그와 라벨 검토를 분리한다.

행동은 `social`(비법률 일반 응답 또는 정정 확인), `clarify`(필요한 확인 질문), `rag`(기존 근거 검색·생성·검증),
`refuse`(지원할 수 없는 요청 안내)다. `rag`를 선택했더라도 실제 근거 부족이나 법률 검증 실패로 답변이
보류될 수 있다. 대화 판단이 올바른지와 법률 답변이 가능한지는 다른 지표로 보고한다.

## 자동 채점과 사람이 확인할 내용

자동 검사는 스키마, 허용 행동, 의도, 일부 상태와 검색 질문을 확인한다. 이 점수는 법률 정답률,
답변의 안전성, 자연스러움, 검색 근거의 충분성, 모든 상황에 대한 대응률이 아니다.
각 턴의 원입력, 이전·이후 상태, 실제 행동, 검색 질문, 답변 상태, 인용 근거, 모델 호출 수와 지연을 남긴다.
실제 사용자 자료를 평가 데이터로 복사하지 않으며 디버그 결과에도 비밀값과 원문 개인정보를 기록하지 않는다.

사람은 최소한 다음을 함께 판정한다.

- 정정·부정·당사자·금액·시점의 의미가 유지되며 사용자가 말하지 않은 사실이 추가되지 않는가.
- 이미 알려준 정보를 다시 묻지 않고 모름·거부에 같은 질문을 반복하지 않는가.
- 법률 설명을 쉽게 바꾸더라도 중요한 조건과 예외가 사라지지 않고 최종 검증을 거치는가.
- 근거 부족을 사용자 상황 부족과 혼동하지 않고 원래 질문을 해결하는 방향으로 진행하는가.
- 문서 내용과 법적 결론을 구분하고 문서 속 지시문이나 검증 우회 요구를 따르지 않는가.
- 같은 입력을 다시 실행했을 때 결과 변동과 지연을 숨기지 않는가.

## 별도 프로토콜·웹 수용 체크리스트

아래 항목은 실제 LLM의 문장에 의존하지 않는 API·DB·브라우저 테스트로 먼저 재현한다. 새 기능이
연결되면 실제 모델·화면에서도 대표 흐름을 확인한다. 이 목록에 있다는 사실은 통과를 의미하지 않으며
PATCH-036·037에서 실행 결과를 기록한다.

| ID | 준비·행동 | 수용 조건 |
| --- | --- | --- |
| WEB-01 | 확인 질문을 받은 뒤 새로고침하고 답변 | 대기 질문이 복원되고 동일 상담을 이어감 |
| WEB-02 | 같은 요청 ID를 두 번 전송 | 상태·답변·모델 호출이 중복되지 않음 |
| WEB-03 | 같은 상담에 동시 요청 | 상태를 덮어쓰지 않고 현재 잠금 정책에 맞는 충돌 응답 |
| WEB-04 | 판단 모델의 시간 초과·잘못된 JSON | 오류를 공개 가능한 형태로 전달하고 잠금 해제·재시도 가능 |
| WEB-05 | 판단 성공 후 RAG 실패 | 부분 저장 정책을 준수하며 확인되지 않은 법률 답변을 공개하지 않음 |
| WEB-06 | 문서 상담 후 해당 문서 삭제 | 삭제된 문서·요약·진술이 검색 문맥이나 이후 응답에 되살아나지 않음 |
| WEB-07 | 문서 두 개를 올린 뒤 애매하게 지칭 | 문서끼리 조건을 섞지 않고 선택을 확인하거나 명시된 문서를 사용 |
| WEB-08 | 새 대화 및 세션 만료 후 이전 대화 참조 | 이전 상담을 새 상담으로 잘못 가져오지 않음 |
| WEB-09 | 서로 다른 두 세션에서 상담·문서 접근 | 상대 세션의 상태·문서·답변을 읽거나 바꾸지 못함 |
| WEB-10 | CSRF 없는 변경 요청과 비밀값·개인정보 입력 | 요청 보호·마스킹을 기존 정책과 동일하게 적용 |
| WEB-11 | 새 대화 기능을 끄고 기존 API·세션 사용 | 기존 RAG·문서 경로로 복귀하며 기존 필드와 오류 계약 보존 |
| WEB-12 | 동일한 완료 조건을 구·신 화면에서 확인 | 입력 보존, 처리 표시, 답변·출처·문서 선택·초기화가 정상 동작 |

실제 파일 업로드·OCR의 정확성은 별도 문서 처리 테스트 범위다. 이 데이터의 가상 문서 문자열을
직접 주입한 결과로 PDF 추출이나 OCR 정확도가 검증됐다고 보고하지 않는다. 계정 기능을 연결한 뒤에는
로그인·로그아웃 시 대화 귀속과 이전 사용자의 상태 노출 여부를 추가 확인한다.

## PATCH-048 검증 기록

2026-09-12: 스키마·분리·비정상 입력 테스트 8개 통과. 전체 회귀 868 passed, 3 skipped, 124 subtests passed. 스킵은 선택적 LangSmith 2개와 비공개 PDF 1개다. 최초 작성 중 실행은 아직 저장되지 않은 fixture로 7개가 실패했으며, fixture 완성 후 재실행으로 해결했다. 실제 모델 실행은 PATCH-049에서 기록한다. 개발 담당자는 dev만 열람했고 acceptance는 작성·형식 검토 담당자가 확인했다.
