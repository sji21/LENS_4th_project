# 검증 DB 묶음 재현·복원 (일반 설치 아님)

**일반 서버 설치는 ZIP 없이 [원천 기반 구축](server-data-setup.md)을 사용합니다.** 아래는 이전 평가와 동일한 DB를 복원하는 별도 검증용 경로입니다.

검증된 PATCH-027 데이터 묶음을 빈 환경에 최초 설치하거나 기본143조문(일반133·민법10)에서204조문(일반178·민법26)으로 전환합니다. SQLite·청크·기본/민법 Chroma 인덱스·검색 프로필을 함께 적용합니다.

## 원천 방식으로 이미 구축한 DB가 있다면

`index/server-build.json`이 있는 DB는 이 고정 묶음 도구의 대상이 아닙니다. `status/apply/restore`는 해시 오류 대신 원천 구축 DB임을 설명하고 변경 없이 중단합니다. 이 감지는 DB가 정상이라는 판정이 아닙니다. 원천 DB의 확인·복구는 `setup_data.py`와 명시적 `--rebuild`를 사용합니다.

고정 평가를 재현하려면 **같은 평가 코드 버전의 별도 체크아웃**을 만들고, 그 체크아웃의 아직 실행 DB가 없는 `data`에 검증 묶음을 설치하세요. 저장소에 추적된 `data/eval` 등 원천/평가 자료는 그대로 둡니다. 기존 원천 DB나 `data` 전체를 지우지 않습니다. 기존 원천 DB에서 고정 묶음으로 직접 전환·복원하는 옵션은 현재 제공하지 않습니다.

## 먼저 받을 자료: ‘검증된 확대 데이터 폴더’

이 표현은 다운로드 사이트나 새로 만들 폴더가 아니라 **리트리버 담당자가 적재·검증한 실행용 데이터**를 뜻합니다. Git에는 이 실행 자료가 없으므로 담당자에게 데이터 묶음을 받아 압축을 해제하세요. 전달할 내용은 아래와 같습니다. `.env`, API 키, `.venv`, 임의의 다른 DB는 포함하지 않습니다.

```text
data/                         ← 실행기가 물어볼 때 이 폴더를 선택
  chunks/
    chunks.jsonl              # 일반 법령+민법
    civil.jsonl
    cases.jsonl
    guides.jsonl
  database/
    knowledge.sqlite3
    civil.sqlite3
  index/
    chroma_kurev1_1024/        # 하위 파일 전체 필요
    chroma_civil_kurev1_1024/  # 하위 파일 전체 필요
    retrieval-profile.json
```

예를 들어 맥에서 `Downloads/lens-data/data/chunks`가 보인다면 입력할 경로는 `/Users/사용자이름/Downloads/lens-data/data`입니다. 압축 파일 자체나 `chunks` 폴더를 선택하지 않습니다. 압축은 저장소 밖에 풀고, 원본 자료를 대상 저장소의 `data`에 수동으로 덮어쓰지 마세요. 전달된 자료도 실행기가 기존 평가 기록의 해시·내용·검색 결과와 대조합니다. 묶음 자체는 임베딩 모델을 포함하지 않습니다.

## 검증 DB 복원 실행

Python 3.11과 Git을 설치하고 저장소 루트에서 실행합니다.

| 환경 | 명령 |
| --- | --- |
| Windows | `py -3.11 setup_data.py --validation-bundle` |
| macOS | `python3.11 setup_data.py --validation-bundle` |

`.venv`를 만들고 `pip install -r requirements.txt`로 요구 모듈을 확인·설치한 뒤 `pip check`와 실제 DB 모듈 로딩을 검사합니다. KURE는 평가 기록에 고정된 버전을 다운로드하고 파일 해시를 확인합니다. 준비가 끝난 뒤 아래 DB 3단계가 진행됩니다. Python 자체는 자동 설치하지 않습니다.

- 자료 전달 전 환경만 준비: 명령 뒤에 `--prepare-only`.
- 다운로드·DB 적용 없는 환경 점검: `--check`.
- 폴더를 미리 지정: `--source '/Users/사용자이름/Downloads/lens-data/data'`.
- 모듈 설치나 모델 확인 실패 시 DB를 변경하지 않고 오류를 표시합니다. 패키지는 버전 고정 전체 잠금 파일이 아니므로 맥 결과 재현은 별도 확인이 필요합니다.
- 이 고정 평가 재현 경로의 모델 검증 위치는 기본 `~/.cache/huggingface/hub`입니다. 일반 서버 구축과 달리 사용자 지정 HF 캐시로235입력 재현을 지원하지 않습니다. 다른 KURE 버전을 자동 교체하지 않습니다.

## 환경 준비가 끝난 뒤 DB만 실행

프로젝트의 `.venv`와 KURE 모델을 준비하고 앱을 종료한 뒤 저장소 루트에서 실행합니다.

Windows PowerShell:

```powershell
.\manage-data.ps1
```

macOS 터미널:

```bash
.venv/bin/python -X utf8 -m scripts.manage_retrieval_data
```

`.ps1`은 Windows용입니다. macOS에서는 맥에서 만든 `.venv`에 의존성과 KURE 모델을 준비하세요. Windows의 가상환경을 그대로 복사해 사용하지 않습니다. 같은 Python 진입점을 호출하지만 **macOS에서 실제 실행·Chroma 호환성·검색 결과 재현은 아직 검증하지 않았습니다.**

맥에서 원본을 미리 지정하려면 위 명령 뒤에 `--source '<검증된 데이터 폴더>'`를 붙입니다. 상태 확인은 `status`, 복구는 `restore --backup '<안내된 백업 폴더>'`를 붙입니다.

화면에는 **[1/3] DB 체크 → [2/3] DB 적용 → [3/3] 결과 확인** 순서로 표시합니다. 같은 데이터가 있으면 추가 불필요·변경 없음으로 종료합니다. 적용이 필요한 경우에만 검증된 확대 데이터 폴더를 입력받습니다. 원본이 없는 상태에서 자동으로 임의의 법령을 수집하거나 선택하지 않습니다.

자동 실행 환경에서는 `.\manage-data.ps1 -Source '<검증된 데이터 폴더>'`로 원본을 지정합니다. 입력을 받을 수 없는데 원본도 없으면 대기하지 않고 오류로 종료합니다. 단계별 상세 로그와 백업 경로는 실행 폴더에 남깁니다.

상태만 보려면 `.\manage-data.ps1 status`, 복구하려면 `.\manage-data.ps1 restore -Backup '<안내된 백업 폴더>'`를 사용합니다. PowerShell 대신 `.venv/Scripts/python -X utf8 -m scripts.manage_retrieval_data`도 인자 없이 같은 흐름을 실행합니다. 실행 오류는 종료 코드1, 인자 오류는2입니다.

## 중복·손상 방지

- 동일 프로필 이름만 보지 않고6개 파일의 SHA-256과 두 Chroma 인덱스의 문서·메타데이터·벡터를 검증합니다. 이미 같은 묶음이면 재적재·백업·검색 재실행 없이 종료합니다.
- 파일 내 청크 ID, 법령명·조문·판본, SQLite 조문 키 중복을 검사합니다. 전체 법령 파일에 민법이 포함되고 민법 전용 파일에도 같은 자료가 있는 것은 의도된 구성으로, 두 사본의 내용이 정확히 같은지 검사합니다.
- 상태·중복 검사는 임시 사본에서 실행합니다. Chroma가 읽기 중 내부 파일을 재저장하더라도 실제 데이터에는 영향을 주지 않으며, 별도 검증 프로세스가 종료된 다음 사본을 정리합니다. 상태 확인·적용·복구 명령은 같은 OS 잠금을 사용하며 프로세스 종료 시 잠금은 해제됩니다.
- 빈 환경은 전달받은204조문 묶음으로 최초 설치합니다. 기존143조문과 다른 데이터나 부분 적재 상태는 자동으로 덮어쓰지 않습니다. 이 도구는 승인된 확대 묶음 적용용이며 임의의 새 법령/판본을 자동 채택하지 않습니다. 수동 README6.4~6.5만으로 확대 묶음이 완성되지는 않습니다.
- 적용 전 코드 커밋과 깨끗한 작업 트리가 필요합니다. 폴더는 `tmp/retrieval-data/<시각-고유번호>/`에 자동 생성하고 재사용하지 않습니다.
- 교체·백업 기록 실패는 기존 적재 도구가 원본을 복구합니다. 적용 후 검색 검증 또는 완료 기록 저장이 실패하면 간편 명령이 백업을 복구합니다. Ctrl+C로 사후 검사를 중단해도 하위 프로세스 종료 후 복구합니다. 파일을 교체 중인 하위 apply/restore에는 중단을 바로 전달하지 않고 해당 작업 종료를 기다려 복구와 동시에 쓰지 않도록 합니다. 최초 설치 중 중단되면 이번에 설치한 파일만 실패 폴더로 옮깁니다. 복구 자체가 실패하면 오류를 반환하며 백업과 실패 자료를 보존합니다. 강제 종료·전원 차단은 이 중단 복구의 보장 범위가 아닙니다.
- 최초 설치에는 이전 DB 백업이 없으며, 실패하면 이번 실행이 설치한 파일만 실행 폴더의 `failed/`로 옮깁니다. 저장소의 평가 자료는 유지합니다. 기존 DB 전환용 `restore`는 최초 설치에는 사용하지 않습니다.
- 다른 초기화/직접 적재 명령이나 앱과 동시에 실행하지 않습니다. 이 잠금은 이 간편 명령 간의 동시 실행을 막습니다.

## 기록과 확인

각 실행 폴더의 `preflight/`, `postflight/`, `backup/receipt.json`, `result.json`에서 검증·백업 결과를 확인합니다. `status`의 `baseline`은 일반133·민법10, `installed`는 일반178·민법26입니다. 판례26·안내6은 그대로 유지합니다. 사후235입력 확인은 기존 최종 검색 결과와의 재현 검사이며 새로운 독립 평가나 LLM 답변 평가가 아닙니다.


### 공용 DB 경로의 동시 실행 방지

잠금은 체크아웃 위치가 아니라 실제 대상 DB 폴더의 `.retrieval-data.lock`에 걸립니다. 서로 다른 체크아웃에서 같은 `--data-root`를 지정하거나 기본 설치·검증 도구를 함께 실행해도 같은 대상은 동시에 수정하지 않습니다. 다른 대상 DB는 별도 잠금을 사용합니다. 잠금 파일은 교체 대상에서 제외하고 삭제하지 않으며, 프로세스가 종료되면 OS 잠금이 해제됩니다. 이전 버전의 설치/복구 작업은 모두 종료한 뒤 갱신된 도구를 실행하세요.
